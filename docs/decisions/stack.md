# Produto, stack e convenções

## Produto

- Site para organizar torneios de Quake Champions: duelo, FFA, FFA por pontos/frags, 2v2, 3v3.
- **Nome: Telefrag** (do usuário, 31/10): termo do Quake sem a marca "Quake", igual em pt e es, e não amarra a plataforma a um torneio (a RageCon é uma comunidade dentro dela). `telefrag.com.br` e `telefrag.gg` estavam livres em 31/10. O nome interno (bancos, roles, prefixo do Redis) também virou `telefrag` em 31/10; ainda chamam `tournaments` a pasta do checkout e o repositório no GitHub, e o domínio não mudou.
- **Logo**: o banner do usuário vetorizado à mão em `docs/brand/` (branco, como o original) e em `web/src/shared/lib/logo.ts` (os mesmos caminhos). No cabeçalho, na cor do texto do tema e só o ícone abaixo do `md` (a barra de ações não deixa espaço). Ícones do site (favicon, tela inicial) com o ícone em branco no fundo `#161616`, que funciona em aba clara e escura.
- Português e espanhol (a comunidade joga muito com argentinos); inglês (en-US) desde 04/11, a pedido do usuário. O padrão continua `pt`. No inglês: data `mm/dd/yyyy` nos campos e hora de 12 h (AM/PM) nas frases (`LocalDayTime`), mas 24 h no `TimePicker`; "match" é a série e "game" a partida; chave principal `W1.2` e repescagem `L1.2` (no pt/es a repescagem é `R`); "walkover" no lugar de W.O.; nome do torneio e demais textos do organizador seguem o idioma original com traduções opcionais, como nos outros.
- Multi-tenant: qualquer usuário logado cria tenants, com limite por usuário. Jogadores entram num tenant só por link de convite e têm um perfil por tenant.
- Primeiro formato de ponta a ponta: **duelo**. Exercita chave, veto, pick/ban, não repetição, resultado e rating; os outros reaproveitam.

## Stack

| Camada | Escolha |
|---|---|
| Backend | Rust + Axum + sqlx (SQL puro, sem ORM) + utoipa (OpenAPI em `/openapi.json`, Scalar em `/docs`) |
| Frontend | Next.js (App Router), **só apresentação**, next-intl, Bun (pacotes e scripts), Biome |
| Tipos no front | gerados do OpenAPI com openapi-typescript |
| Banco | Postgres. Dev: cluster local. Prod: database com usuário próprio no projeto Supabase us-east-1 existente |
| Redis | Dado efêmero (ver "Redis"). Dev: local, database 1. Prod: Upstash grátis, database 0 |
| Email | Resend pela API HTTP (ver `mail.md`) |
| Tempo real | WebSocket no Axum, `tokio::broadcast` em memória (uma instância); `LISTEN/NOTIFY` se um dia houver mais de uma |
| Storage | API S3 genérica, provedor por variável de ambiente. Prod: AWS S3 (ver `screenshots.md`) |
| Observabilidade | Sentry no Rust e no Next |
| Hospedagem | API no Render (Virgínia, free + uptime monitor). Front na Vercel (funções em `iad1`, perto da API). Domínio próprio: `telefrag.com.br` e `api.telefrag.com.br`; o staging em `staging.` e `api.staging.` (o cookie pede o mesmo site, `auth.md`, "Sessão") |

- **Rust**: interesse em aprender; o Scalar em `/docs` (no lugar do Swagger UI) permite acompanhar e testar os endpoints.
- **Bun só como gerenciador de pacotes e executor de scripts.** A Vercel detecta o `bun.lock`; as funções seguem no runtime Node (o do Bun na Vercel ainda é beta), e o `next` local também roda em Node.
- **Nada de ferramenta global além de Rust e Bun.** Sem pnpm e sem sqlx-cli: as migrations são arquivos à mão, aplicados por `cargo run -p migrate` (sem macros de query, então compila antes de a tabela existir) e pela API ao subir. O build sem banco (Render) usa o modo offline do sqlx: `bun scripts/sqlx-prepare.ts` faz o papel do `cargo sqlx prepare` (com `SQLX_OFFLINE_DIR`, as próprias macros gravam o `.sqlx/`), que vai para o repositório; o Render compila com `SQLX_OFFLINE=true`.
- **Next só apresentação**: renderiza no servidor as páginas públicas (preview do link no Discord), cuida das rotas por idioma e nunca acessa o banco.
- **Supabase é só host de Postgres**, via connection string. Nada de Supabase Auth, Realtime, Storage ou supabase-js, para evitar lock-in.
- **Render free**: 750 h/mês por workspace, o que cabe em **um** serviço sempre ligado.
- **Render → Supabase**: a conexão direta é só IPv6 e costuma falhar no Render; use o pooler em **modo sessão**, com o usuário próprio (`usuario.<project-ref>`). Se o pooler não aceitar outro database, um schema dedicado dentro de `postgres`.
- **Latência** (medido em 01/11): os jogadores estão em São Paulo e a API na Virgínia (~0,45 s de ida e volta); uma rota trivial leva ~150 ms com a conexão quente, e a borda do Cloudflare às vezes abre conexão nova até o Render (+270 ms). Por isso o CORS responde com `max_age` de 2 h (o teto do Chrome): sem ele, o navegador guarda o preflight por 5 s e cada POST com JSON pagava um `OPTIONS` antes.
- **Idas ao banco por requisição** (01/11, `tests/api/matches/cost.rs`, que imprime a lista com `--nocapture` e tem um teto por rota): cada ida Render → Supabase custa poucos ms, e o clique faz várias em série. Passo do veto de 26 queries + 3 pings para 14 + 2; envio de partida de 29 para 16; confirmação de 25 para 14; leitura da série de 14 + 3 para 9 + 2; a página da série (7 pedidos do Next) de 45 + 16 para 26 + 11. Como: o `TenantMember` lê a conta e a participação numa query só (a sessão continua no Redis); `tournaments::find` traz fases, pool e traduções agregadas em JSON (4 → 1) e o slug da comunidade, para os avisos da chave não lerem o torneio de novo; a ação lê a fase uma vez com o torneio travado e confere em memória as confirmações vencidas (antes, uma query e uma segunda leitura da fase); depois de gravar, relê só o que gravou (`Stage::refresh`: os eventos do veto, ou as partidas), e o resto do `settle` relê tudo só se mudar mais alguma coisa; o status do torneio só é gravado quando muda; as mudanças de partida vão ao outbox num insert só. A regra de travar o torneio antes de ler o estado não mudou. `test_before_acquire` fica ligado: o sqlx não repete a query numa conexão que o pooler ou uma manutenção do Supabase derrubou, e o ping é uma ida curta na mesma região; o que caiu foi o número de conexões tiradas do pool por requisição (de 3 para 2).
- **Idas ao banco, segunda passada** (04/11): a fase (`stage::load`) lê os times e uma query só com séries decididas, mapas, pareamentos, eventos de veto, escalações e campeões agregados em JSON (2 idas no lugar de 4 a 7); os ids e flags entram como `(select $n)` para o Postgres não replanejar a cada chamada (0,48 ms de planejamento contra 0,01 ms). GET série 9 → 5, passo do veto 14 → 10, envio 16 → 13, confirmação 14 → 11, página da série 26 → 19. `/me/tournaments` (N+1 por comunidade e torneio) 27 → 8, e o perfil do membro 27 → 10, com os torneios, times e participações de todas as comunidades numa query cada; só os torneios em andamento leem a fase inteira. A página de um torneio pede `GET /tenants/{slug}/tournaments/{t}/mine` (4 idas) em vez da lista inteira. Os campeões não ficam em cache de processo: os testes mudam a tabela em execução.
- **Trabalho de fundo** (04/11; o Render free tem 0,1 CPU e o pool, 5 conexões): o agendador de 10 s passou de 2 varreduras do veto (cada uma relendo a fase de todos os N torneios com veto aberto) e um despertar do despachante e do relógio por passada, emitisse ou não, para 14 queries + 12 pings sem veto nenhum (as etapas dele, cada uma pegando uma conexão; a do advisory lock fica presa à passada, que é o que o deixa soltar sozinho). O relógio do veto relê só o que mudou (`veto.md`), e o despachante ocioso olha o outbox a cada 60 s (2 queries, sem o `delete` vazio). Medido com um torneio aberto: com N torneios, de 19 + 12N queries a cada 10 s para ~15 + N.
- **Pool**: `max_connections` 5 e `min_connections` 0 (do usuário: não ocupar o pooler do Supabase sem uso); `max_lifetime` de 2 h no lugar dos 30 min do sqlx, porque cada conexão nova é TLS + SCRAM pelo Supavisor, paga por quem a abre (com as 5 abertas, uma a cada ~24 min em vez de a cada 6); `idle_timeout` de 10 min (o padrão). O sqlx 0.9 devolve as ociosas em fila (FIFO), e o agendador pega uma por etapa: na prática, a conexão ociosa não chega aos 10 min, e o pool fica no que já abriu até a vida acabar.
- **`GET /maps`** sai com `Cache-Control: public, max-age=300`: é a mesma lista para todos (sem sessão nem idioma) e só muda por migration. Sem compressão nem ETag na API (0,1 CPU; a borda do Cloudflare comprime).

## Redis

Upstash grátis: 256 MB e 500 mil comandos por mês (~16 mil por dia); passar da cota faz os comandos falharem até o mês virar.

- **Só dado efêmero, que some sozinho com TTL**: a cópia das sessões, o cadastro esperando confirmação (conta que ninguém confirma não chega ao banco), links e códigos de entrar por email e de troca de email, a espera e o teto do dia dos envios de email, o vínculo de provedor autorizado por 10 minutos. Sessão no Postgres sobrevivia a deploy, mas a tabela só crescia; no Redis expira sozinha e tira as escritas de login do banco.
- **Sessões em memória** (do usuário, 05/11): toda requisição logada fazia um `HGET`, uma ida ao Upstash por chamada; uma noite de torneio com 32 jogadores recarregando a chave a cada 30 s por 3 horas, ~4 chamadas por página, gastava ~46 mil comandos. Agora a memória do processo responde a toda leitura (`auth/session_store.rs`), e o Redis só guarda entre os boots: lido ao subir e 5 minutos depois. Toda escrita vai primeiro a ele e depois à memória; falhou, nada muda e a rota responde 500. Requisição logada: 0 comandos. Entrar com senha: 1 (`SETEX`; eram 10). Sair: 1 (`DEL`; eram 3). Subir: `SCAN` + `MGET` por mil chaves do database, seja quantas forem as sessões, o motivo do JSON no lugar do hash do Redis (até o formato antigo sumir, mais um `HGETALL` por sessão antiga). Memória: no máximo ~0,5 kB por sessão. Vale porque a API roda em uma instância só, como o `tokio::broadcast` e o `WindowLimit`; com duas, uma não veria o logout da outra.
  - **Num deploy**, a instância antiga atende até a nova ficar no ar, e a nova já leu o Redis. A segunda leitura traz o que a antiga gravou nesse meio tempo: até ela, a sessão encerrada na antiga vale na nova, e quem entrou na antiga recebe 401 e entra de novo. Aceito por ser curto e raro. Procurar no Redis toda sessão desconhecida fecharia a segunda parte, mas cada cookie inventado gastaria um comando.
  - **Em desenvolvimento** (sem `COOKIE_SECURE`), a sessão desconhecida é procurada no Redis: scripts locais criam sessão direto nele com a API no ar, e duas APIs locais dividem o prefixo.
- **Limites em memória** (05/11): as tentativas de senha e os pedidos de email por IP e por conta usam `WindowLimit`. Eram 4 a 5 e 2 a 3 comandos por pedido, gastos antes de qualquer outra defesa: quem insistisse gastaria a cota, e passar dela derruba o login de todos. Um deploy zera as contagens, e a janela conta do primeiro pedido, não mais da hora cheia. Ficam no Redis o teto do dia (um deploy não pode zerar o limite do provedor), a espera de 60 s, os links e códigos e o cadastro pendente: atravessam um deploy e são poucos, porque cada um acompanha um email (no máximo 90 por dia).
- **Cota**: nenhum comando no caminho de toda requisição; o que sobra é por evento (entrar, sair, pedir email, subir). Se apertar: pago por uso (US$ 0,20 por 100 mil comandos) ou o fixo de 250 MB (US$ 10/mês). Pipe e MULTI juntam idas e voltas, mas cada comando deles conta.
- **Fora, por ora**:
  - cache de leitura: chave e torneio mudam com o tempo, parte da resposta depende de quem vê, e cada acerto também gasta cota. Só depois de medir;
  - locks: a concorrência já é `select ... for update` na transação, mais correto que um lock fora dela. O agendador do tempo real usa advisory lock do Postgres, que não gasta cota;
  - tempo real entre instâncias (continua `tokio::broadcast`) e rate limit por conta nas escritas (não pedido);
  - a sala de veto (do usuário, 03/11): fica no Postgres. Cada comando conta na mesma cota das sessões, e um abuso de quem cria sala sem login derrubaria o login de todos; o Redis também não lista os prazos vencidos, que o relógio precisa achar.
- **Sem Redis a API não sobe** (`REDIS_URL` obrigatória, e ela lê as sessões ao subir: sem elas, todo mundo perderia o login). Se cair depois, ou se a cota acabar, quem está logado segue navegando, e entrar, sair e o que manda email respondem 500. O `/health` não consulta o Redis (o monitor de uptime gastaria a cota). A API lê o Redis antes das migrations: sem ele, o deploy falha sem mexer no banco e a instância antiga segue no ar.
- **Conexão**: `ConnectionManager` do redis-rs (abre no primeiro comando, reconecta; o comando que falha por conexão parada tenta de novo uma vez). TLS (`rediss://`) pelo rustls com o provedor aws-lc instalado no `main`: com ring (sqlx) e aws-lc (reqwest) ativos o rustls não escolhe sozinho e entra em pânico.
- **Database e prefixo**: um database só (local, o 1: os outros são de outros projetos do usuário; Upstash, o 0, o único). Toda chave passa por `Redis::key` com `REDIS_PREFIX` (padrão `telefrag:`), para checkout principal e worktrees dividirem o database. Os testes usam `test:{banco}:{empréstimo}:`; a execução seguinte, com o lock da suíte, apaga todo `test:*` antes do primeiro teste (senão chegaram a 39 mil chaves; hoje ~1.900).

## Scanners

Quem pede `/.env`, `/wp-login.php` e afins tem o IP banido por 7 dias, e dali em diante toda rota responde 404 vazio, sem dizer que houve ban (do usuário, 05/11). Na API, `scanners/`; no front, `features/scanners`, no proxy. Sem `INTERNAL_API_SECRET` nos dois, fica tudo desligado.

- **404 seco, sem honeypot**: `.env` falsa ou `wp-admin` falso marcam o site como alvo nas listas de quem varre e trazem mais tráfego; o valor de um honeypot está em alguém ler o que ele colhe, e ninguém lê; o repositório é público, então a isca também é. Na API, a resposta do banido é a de uma rota que não existe, cabeçalho a cabeçalho (teste); `/internal/bans` sem o segredo, também.
- **Só o que nenhum cliente legítimo pede**: um pedaço do caminho que começa com ponto (menos `/.well-known`), extensões de outras stacks e de backup, nomes como `wp-admin` e `phpmyadmin`. Na API, só rota que não existe denuncia; no front, nada depois do idioma (`/pt/solr` pode ser uma comunidade). As listas estão repetidas em `traps.rs` e `traps.ts`.
- **Navegador nunca é banido** (`Sec-Fetch-*`): sem isto, um link ou um `<img>` para `/wp-admin` tiraria o site de um adversário no dia do torneio. **Crawler que diz o nome também não**: um link em qualquer site baniria o Google (o site sairia da busca) e o Discord (sem prévia). Quem forja um dos dois só escapa do ban.
- **Sessão válida passa pelo ban** (no front, a presença do cookie): é quem divide o IP com o scanner (CGNAT), que veria o site sumir sem explicação. O scanner não tem sessão.
- **Servidor do Next nunca é banido** (`x-internal-secret`, em `serverApi`): ele sai pelos IPs da Vercel, divididos com outros clientes dela; sem isto, o scanner de um deles derrubaria as páginas do site. Pedido novo do servidor à API passa por `serverApi` ou leva `internalHeaders()`.
- **7 dias**: quem volta depois disso se bane de novo no primeiro pedido, então mais tempo não compra nada, e o IP pode já ser de outra pessoa.
- **Memória e cota**: lido da memória a cada requisição; a cópia no Redis é um sorted set, gravado a cada 5 minutos num ZADD só (no máximo ~17 mil comandos por mês, com ban novo o tempo todo) e lido ao subir. Teto de 50 mil IPs; passando dele, os novos só recebem o 404 do caminho.
- **Front**: a lista vem da API a cada 5 minutos, em segundo plano e por instância, numa variável do módulo (o proxy não espera a API, e a instância nova deixa passar até a primeira leitura). O IP vem do `x-real-ip`, que a Vercel grava por cima do que o cliente manda.
- **Tirar um ban**: `curl -X DELETE -H "x-internal-secret: $SEGREDO" -d <ip> https://api.telefrag.com.br/internal/bans` (o log do Render diz `scanner banido`, com o IP e o caminho). `GET` no mesmo endereço lista.
- **`/openapi.json` e `/docs`** só sem `COOKIE_SECURE`, ou com `API_DOCS=true`: num ambiente publicado, são o mapa da API para quem varre.
- **O que não dá para esconder**: antes do primeiro pedido denunciado, o site é uma página Next como qualquer outra; a Vercel, o Render e o Cloudflare põem cabeçalhos próprios (`server`, `x-vercel-id`, `rndr-id`, `cf-ray`) em toda resposta, inclusive no 404; e o que está no build (`/_next/static`) segue acessível a quem souber o endereço. Quem comparar de outro IP descobre o ban: o alvo são os robôs.

## Ids

- **Chave interna**: `bigint generated always as identity` (users, tenants, torneios e o que vier). O Postgres é um só e gera os ids, então UUID/ULID não ajudam: 8 bytes contra 16, sequenciais (índice compacto) e cabem no `number` do JS. `tenant_id` também é bigint (num índice composto com outro bigint, um `int4` não economiza por causa do alinhamento).
- **Não escondemos esses ids**: toda rota que recebe um id confere a participação no tenant, então enumerar não dá acesso a nada.
- **Tabela de ligação usa chave natural**: `tenant_members (tenant_id, user_id)`, `user_identities (provider, provider_user_id)`, `participants (tournament_id, user_id)`. Quem ocupa um lado da chave é o time (`teams`, id bigint), que vira o `ParticipantId` (`engine::core::ParticipantId(i64)`; o `engine` não depende de `uuid`).
- **Identificador público e legível**: slug (tenant, torneio). Usuário não tem identificador público; se um dia tiver perfil público, ganha um handle.
- **Segredos** (sessão, links por email): aleatórios, só o SHA-256 guardado, no Redis. Os links têm 128 bits em base58 (22 caracteres, sem `0/O/I/l`, para o duplo clique selecionar tudo); a sessão, 256 bits em base64url (só no cookie).
- **Exceção: o token do link de convite fica em claro** (do usuário, 03/11): `tenants.invite_token` e `tournaments.invite_token`, para organizer e owner verem e copiarem a qualquer hora (`tenants.md`, "Convites"). O link não é credencial: é público, dá só entrada como player e se troca em dois cliques. Continua com 128 bits aleatórios, do mesmo gerador (`token::random_token`), para ninguém adivinhar um.
- **Exceção: os tokens da sala de veto ficam em claro** (assumido, 03/11; `veto_rooms.manage_token`, `spectator_token`, `veto_room_seats.token`): a página de gestão mostra todos de novo, e recarregar não pode perdê-los. Diferente do convite, cada um é a credencial de um lugar, mas vive no máximo 24 h e não dá acesso a nada além da sala. 128 bits do mesmo gerador.
- Se um dia houver ids gerados fora do banco: `uuidv7()`, nativo no PG18.

## Repositório e CI

- Privado agora, público depois: nenhum segredo no código (`.env.example` versionado), histórico limpo.
- GitHub Actions com cache de build Rust (o plano privado tem 2.000 min/mês). Em pull request roda só o lado cujos arquivos mudaram (`dorny/paths-filter`); em push na `main` e no `staging`, os dois (a integração vai para o `staging`; sem ele, um commit só via a suíte ao chegar na `main`); execução antiga do mesmo ref é cancelada.
- A conferência do `.sqlx/` regrava as queries num diretório à parte e compara (`diff -r`), reaproveitando as dependências compiladas (~1 min), em vez de rodar `sqlx-prepare.ts` (compilaria tudo de novo). Existe porque `.sqlx/` sobrando ou diferente seria invisível ao clippy offline.
- **`.sqlx/` sempre de um banco novo**, só com as migrations: o sqlx deduz a nulidade das colunas do plano da query (`EXPLAIN`), que muda com os dados. Gerado no banco de dev, a CI ficava vermelha sem nada errado (5 execuções seguidas em 01/11). Em banco novo, Windows e Linux deram os mesmos 312 arquivos.
- Banco de dev: cluster Postgres local; usuário `telefrag` sem senha (`trust` no `pg_hba.conf`), restrito ao próprio banco e aos de teste.

## Organização do código

Regras em `backend/CLAUDE.md` e `web/CLAUDE.md` (o Claude Code os carrega ao abrir arquivos da pasta; uma skill dependeria de ser acionada e um doc importado na raiz custaria contexto em toda sessão).

- **Por domínio dos dois lados**, com os mesmos nomes, e `shared/` para o genérico.
- **API: SQL só em `<domínio>/db.rs`**: achar uma query é abrir um arquivo, e handler com transação não fica longo.
- **Testes de rota num binário só** (`tests/api/`), um arquivo por domínio: no Windows cada binário de teste demora para linkar.
- **Front sem shadcn por enquanto**: primitivos próprios em `shared/ui`, com os nomes de variante do shadcn, para ele entrar depois sem mudar quem usa.

## Testes

Uma suíte levou perto de uma hora com outras sessões rodando; um cluster Postgres separado para os testes foi recusado.

- **Bancos reaproveitados** (`tests/api/db.rs`), no lugar do `sqlx::test` (criava e apagava um banco por teste; o `drop database` força um checkpoint no servidor inteiro, 107 s com três suítes): cada banco principal tem 8 bancos de teste (`TEST_DATABASES`), `_sqlx_test_<banco>_t<n>`, migrados uma vez e recriados só quando as migrations aplicadas não batem com as do código. Antes de cada teste as tabelas são esvaziadas e as linhas das migrations (campeões, mapas) voltam de uma cópia. Descartado: um banco só (os testes contam com banco vazio e rodam em paralelo) e uma transação por teste (os handlers fazem commit). A suíte foi de ~1 hora para ~40 s.
- **Esvaziar por `delete`, não `truncate`**: o `truncate ... restart identity` troca os arquivos de cada tabela, e no Windows com antivírus isso custava 0,13 s por teste parado e 9 s com outras sessões compilando (suíte de 65 s a 760 s). O `delete` de tabelas quase vazias fica na memória: 9 a 23 s. Comunidades e usuários saem primeiro (a cascata leva o resto) e cada tabela numa subtransação, repetindo a que um trigger recusou. `session_replication_role = replica` pediria `grant` de superusuário em cada máquina. 8 bancos porque 16 ganha pouco e, com o pool cheio (8 conexões por teste), passaria das 100 conexões do Postgres.
- **Uma suíte por vez na máquina**: o binário pega um lock de arquivo na pasta temporária (`telefrag-api-tests.lock`); a de outra sessão espera. Dez suítes juntas levaram o mesmo que em fila, mas ninguém via resultado antes do fim, e os testes do Discord que dependem do relógio falharam sob carga.
- **Teste que não cobre nada novo sai**: só fica o que exercita um caminho, regra, código de erro ou constraint que nenhum outro exercita. Juntar testes pequenos num só ficou de fora: um teste a mais custa milissegundos, e o separado diz melhor o que quebrou.
