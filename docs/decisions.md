# Decisões do projeto

Registro das decisões tomadas antes do início do código, com o motivo de cada uma. Atualize quando algo mudar.

## Produto

- Site web para organizar torneios de Quake Champions: duelo, FFA, FFA por pontos/frags, 2v2, 3v3.
- Idiomas: português e espanhol (a comunidade joga muito com argentinos). Tudo localizável.
- Multi-tenant: qualquer usuário logado cria tenants, com limite por usuário. Torneios pertencem a um tenant.
- Jogadores entram num tenant só por link de convite e têm um perfil por tenant.
- Primeiro formato de ponta a ponta: **duelo**. Exercita chave, veto, pick/ban, não repetição, resultado e rating; os outros reaproveitam.

## Stack

| Camada | Escolha |
|---|---|
| Backend | Rust + Axum + sqlx (SQL puro, sem ORM) + utoipa (OpenAPI em `/openapi.json`, Scalar em `/docs`) |
| Frontend | Next.js (App Router), **só apresentação**, next-intl, Bun (pacotes e scripts), Biome (lint e formatação) |
| Tipos no front | gerados do OpenAPI com openapi-typescript |
| Banco | Postgres. Dev: cluster local. Prod: database com usuário próprio no projeto Supabase us-east-1 existente |
| Redis | Sessões, tentativas de senha, cadastros esperando o link do email, links de uso único e limites de envio. Dev: servidor local, database 1 (Memurai no Windows; os outros databases ficam para outros projetos). Prod: Upstash grátis, database 0 (256 MB, 500 mil comandos por mês, `rediss://`). Ver "Redis" |
| Email | Resend pela API HTTP (o Render free bloqueia as portas de SMTP), domínio `magic3t.com.br`. Grátis: 3.000 por mês, 100 por dia. Sem chave, em dev, os emails vão para o log. Ver "Email" |
| Tempo real | WebSocket no Axum, `tokio::broadcast` em memória (uma instância). `LISTEN/NOTIFY` se um dia houver mais de uma |
| Storage | API S3 genérica, provedor por variável de ambiente. Prod: AWS S3, classe Standard, sem CloudFront (ver "Resultados") |
| Observabilidade | Sentry no Rust e no Next |
| Hospedagem | API no Render (Virgínia, free + uptime monitor). Front na Vercel (funções em `iad1`, perto da API). Domínio próprio |

Motivos e cuidados:

- **Rust**: interesse em aprender; o Scalar em `/docs` permite acompanhar e testar os endpoints (trocou o Swagger UI, mais elegante).
- **Bun só como gerenciador de pacotes e executor de scripts.** A Vercel detecta o `bun.lock` e instala com `bun install`. As funções continuam no runtime Node (o runtime Bun na Vercel ainda é beta), e localmente o `next` também roda em Node.
- **Nada de ferramenta global além de Rust e Bun.** Sem pnpm e sem sqlx-cli: as migrations são arquivos criados à mão, aplicados pelo binário `cargo run -p migrate` (que não usa macros de query, então compila mesmo antes da tabela existir) e também pela API ao subir. O build sem banco (Render) usa o modo offline do sqlx: `bun scripts/sqlx-prepare.ts` faz o papel do `cargo sqlx prepare` sem o sqlx-cli (com `SQLX_OFFLINE_DIR` definido, as próprias macros gravam o `.sqlx/`), o `.sqlx/` vai para o repositório e o Render compila com `SQLX_OFFLINE=true`.
- **Next só apresentação**: renderiza no servidor as páginas públicas (preview do link no Discord) e cuida das rotas por idioma. Nunca acessa o banco.
- **Supabase é só host de Postgres**, via connection string. Nada de Supabase Auth, Realtime, Storage ou supabase-js, para evitar lock-in.
- **Render free**: 750 h/mês por workspace, o que cabe em **um** serviço sempre ligado.
- **Conexão Render → Supabase**: a conexão direta é só IPv6 e costuma falhar no Render; use o pooler em **modo sessão**. Teste cedo com o usuário próprio (formato `usuario.<project-ref>`). Se o pooler não aceitar outro database, use um schema dedicado dentro do database `postgres`.

## Redis

Entrou em 2026-10-28, com a instância grátis do Upstash: 256 MB e 500 mil comandos por mês (~16 mil por dia); passar da cota faz os comandos falharem até o mês virar.

- **O que vai: dado efêmero, que some sozinho com TTL.** Sessões e tentativas de senha (escolha do usuário). As sessões no Postgres já sobreviviam a deploy; o ganho é a expiração sozinha (a tabela só crescia), o índice por conta e tirar as escritas de login do banco. Desde o email (2026-10-28): o cadastro com senha esperando o link (pedido do usuário: conta que ninguém confirma não chega ao banco), os links de recuperação de senha e de troca de email e os limites de envio (ver "Email").
- **Cota**: a sessão é o único comando no caminho de cada requisição logada (um `HGET`). Conta de referência: noite de torneio com 32 jogadores recarregando a chave a cada 30 s por 3 horas, com ~4 chamadas à API por página, dá ~46 mil comandos. Se apertar: pago por uso (US$ 0,20 por 100 mil comandos) ou o fixo de 250 MB (US$ 10/mês, sem limite de comandos). Pipe e MULTI juntam idas e voltas, mas cada comando deles conta.
- **O que não vai, por ora**:
  - cache de leitura: a chave e o torneio mudam com o tempo (confirmação por tempo, abertura do check-in), parte da resposta depende de quem vê, e cada acerto também gasta cota. Só depois de medir onde dói;
  - locks: a concorrência já é `select ... for update` dentro da transação, mais correto que um lock fora dela. O agendador do tempo real, com mais de uma instância, usa advisory lock do Postgres, que não gasta cota;
  - tempo real entre instâncias: continua `tokio::broadcast`, e `LISTEN/NOTIFY` se um dia houver mais de uma;
  - limite por conta nas escritas (rate limiting por usuário): não pedido.
- **Sem Redis a API não sobe** (`REDIS_URL` obrigatória e um `PING` ao subir) e, se ele cair, as rotas que leem a sessão respondem 500: as sessões só existem lá. O `/health` não consulta o Redis, porque o monitor de uptime gastaria a cota.
- **Conexão**: `ConnectionManager` do redis-rs, que abre no primeiro comando e reconecta; o comando que falha porque a conexão parada caiu tenta de novo uma vez (`shared/redis.rs`). TLS (`rediss://`) pelo rustls com o provedor aws-lc instalado no `main`: com ring (sqlx) e aws-lc (reqwest) ativos, o rustls não escolhe sozinho, e o primeiro `rediss://` entrava em pânico (conferido).
- **Database e prefixo**: o projeto usa um database só: no Redis local, o 1 (os outros são de outros projetos do usuário); no Upstash, o 0, o único que há. Dentro dele, toda chave passa por `Redis::key`, com `REDIS_PREFIX` (padrão `tournaments:`) na frente, para ambientes deste projeto dividirem o database (checkout principal e worktrees). Os testes usam `test:{execução}:{banco do teste}:`, e as chaves de execuções com mais de uma hora saem na execução seguinte.
- **Deploy**: definir `REDIS_URL` no Render (o `rediss://default:<senha>@<host>:6379` do Upstash) antes de subir a migration `20261103000000_sessions_in_redis`, que apaga `sessions` e `password_failures`. A API confere o Redis (`PING`) antes de aplicar as migrations: sem ele, o deploy falha sem apagar nada, e a instância antiga segue no ar.

## Autenticação

- Própria, em Rust. Três logins: Discord e Google (OAuth2) e nome de usuário + senha.
- `users` + `user_identities (provider, provider_user_id, UNIQUE(provider, provider_user_id))`: uma linha por login de provedor externo (hoje `discord` e `google`; Steam e login por código no futuro são só mais um valor). No máximo um login de cada provedor por usuário (`UNIQUE(user_id, provider)`). Username e senha ficam em `password_credentials` (uma por conta, a chave é o `user_id`), separados desde 2026-10-28 para o hash da senha não conviver com ids de OAuth (pedido do usuário; a migration `20261106000000` moveu as linhas `password`).
- **Username e senha**: o username fica em `password_credentials.username` como digitado e o hash argon2id em `password_hash`. Formato: 3 a 20 letras ou números ASCII, `_`, `.` e `-` (só ASCII para não haver nomes que parecem iguais). Único sem diferenciar maiúsculas (índice em `lower(username)`), e o login também não diferencia. No cadastro o username vira o nome exibido; trocar o username depois não muda o nome. O próprio usuário troca o **nome exibido** na conta (`PATCH /me`, rodada 2b): de 1 a 32 caracteres numa linha, sem espaços nas pontas (assumido: o cadastro não pede nome, ele vem do username; 32 é o limite do apelido, que começa com o nome, e o do Discord). Trocar não muda os apelidos que ele já tem nas comunidades, e o login pelo Discord não sobrescreve o nome. Senha de 8 a 128 caracteres, sem regra de composição (NIST 800-63B).
- **Limite de tentativas por username, no Redis** (`password_failures:{username}`, um zset com o horário de cada erro, que expira com a janela; era a tabela `password_failures` até 2026-10-28): 5 senhas erradas em 15 minutos bloqueiam aquele username até o erro mais antigo sair da janela (429 `auth.too_many_attempts` com os minutos). Vale também para username inexistente, que confere contra um hash fixo para não revelar pelo tempo quem existe. Não usa IP (não depende do `X-Forwarded-For` do Render); o custo é que alguém pode travar o login por senha de outra pessoa por 15 minutos, e o Discord continua entrando.
- **Recuperação de senha por email** (desde 2026-10-28; antes não havia, e o Discord era o backup): o cadastro com senha exige email confirmado, e a senha esquecida volta pelo link mandado a ele. Regras em "Email".
- **Google** (desde 2026-10-29, pedido do usuário: "pede só o necessário"): OpenID Connect com os escopos `openid profile`, que dão o `sub` (o id da conta Google, que não muda nem é reaproveitado, ao contrário do email; check `user_identities_google_sub_format`) e o nome. Sem o escopo `email`: o email da conta daqui só entra confirmado pelo link, e o do Google traria a mesclagem com a conta que já tem aquele endereço. A foto também não é usada: o avatar segue vindo só do Discord, porque a foto do Google é da pessoa e o avatar aparece em listas e chaves públicas. O nome do Google vira o nome exibido da conta nova (numa linha, cortado em 32; sem nome, "Google"), e entrar de novo não o muda, como no Discord. O id token vem direto do endpoint de token, por HTTPS e com o client secret, e por isso a assinatura não é conferida (o próprio Google dispensa nesse caso); emissor e público são. A autorização vai com `prompt=select_account`, para a pessoa ver qual conta usa, também ao vincular. O cookie do state guarda o provedor, e o callback de um recusa o state aberto para o outro (`auth.state_mismatch`). Variáveis: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` e `GOOGLE_REDIRECT_URI`; sem as duas primeiras, 503 `auth.google_not_configured`. O client registrado só aceita o redirect de produção: localmente, o botão para no erro de redirect do Google, e o fluxo é coberto pelos testes de rota com o Google falso.
- **Vincular e desvincular**: quem entrou por um provedor pode criar username e senha depois de ter email confirmado, e qualquer conta pode vincular o provedor que não tem (pelo mesmo OAuth, com a intenção "link" no cookie do state). A conta nunca fica sem login nem com senha sem email: remover a senha exige Discord ou Google vinculado, desvincular um provedor exige senha ou o outro provedor (409 `auth.last_login`), criar a senha exige email (409 `auth.email_required`) e tirar o email exige não ter senha (409 `auth.password_needs_email`). Trocar ou remover a senha pedem a senha atual (com o mesmo limite de tentativas); desvincular um provedor também, se a conta tem senha (`DELETE /auth/{discord|google}` com `current_password` opcional). Na conta sem senha, desvincular só pede a sessão, como tirar o email: com ela já se põe email e cria senha, então pedir algo não protegeria nada (desde 2026-10-29, quando a conta passou a poder ter dois provedores; antes, desvincular o Discord sempre exigia senha). Trocar a senha encerra as outras sessões. Desvincular o Discord tira o avatar, que vinha dele.
- **Senha só com email** (desde 2026-10-28, pedido do usuário): antes, a conta do Discord criava senha sem email, e quem a esquecia ficava preso, porque pôr o email e remover a senha pedem a senha atual. O banco também confere (`password_credentials_email_required`: triggers na criação da senha e na saída do email, com o lock da linha do usuário pondo as duas em fila). As contas com senha e sem email que havia eram de teste: em produção saíram à mão, e em dev ganharam email inventado, antes da migration `20261107000000`, que falha se sobrar alguma em vez de apagar conta. Limite conhecido: quem tem Discord e senha, esquece a senha e perde o acesso ao email não troca nenhum dos dois (entra pelo Discord); se acontecer, a saída pensada é confirmar pelo Discord no lugar da senha atual.
- Vincular um Discord ou uma conta Google que já é login de outra conta é recusado (`auth.discord_taken`, `auth.google_taken`); não há mesclagem de contas.
- Sessão em cookie `HttpOnly; Secure; SameSite=Lax; Domain=.<domínio>`, de 30 dias contados da entrada (sem renovar a cada uso, que gastaria um comando de escrita por requisição). As sessões ficam no Redis desde 2026-10-28 (antes, numa tabela no Postgres; a troca deslogou todo mundo uma vez):
  - `session:{sha256 do token}`: hash com `user_id`, `created_at` e `user_agent` (o do login, até 256 caracteres), com o TTL da sessão. Cada requisição logada faz um `HGET` dela e lê o usuário no banco pela chave primária; o usuário não fica em cache no Redis, para nome, avatar e idioma nunca ficarem velhos.
  - `user_sessions:{user_id}`: zset com os hashes das sessões da conta e a expiração como score, gravado junto com a sessão (MULTI). Serve para listar (`GET /auth/sessions`), encerrar uma (`DELETE /auth/sessions/{id}`, que também apaga o cookie se for a da requisição) e encerrar as outras (`DELETE /auth/sessions` e a troca de senha). As vencidas saem do índice ao criar sessão e ao listar.
  - O `id` público de uma sessão são os 16 primeiros caracteres hexadecimais do hash (64 bits): não serve para entrar, não precisa de outra chave e não se repete entre as sessões de uma conta.
  - Conta apagada direto no banco deixa a sessão no Redis, sem efeito (o usuário não existe mais) até expirar.

## Email

Entrou em 2026-10-28 para a recuperação de senha. Respostas do usuário: qualquer domínio menos descartáveis (não só provedores conhecidos), limites de envio agora e captcha só se aparecer abuso, e o email numa coluna de `users`. As contas antigas com senha e sem email, que primeiro seguiriam entrando com um aviso, saíram no mesmo dia (ver "Senha só com email" em "Autenticação").

- **Provedor**: Resend pela API HTTP (`mail/sender.rs`, `reqwest`), porque o Render free bloqueia as portas 25, 465 e 587 desde 2025-09. Plano grátis: 3.000 por mês e 100 por dia, um domínio (`magic3t.com.br`). Atrás da trait `Mailer`, como o Discord e o Web Push. Variáveis: `RESEND_API_KEY`, `EMAIL_FROM` (`Nome <endereço@magic3t.com.br>`) e `EMAIL_DAILY_LIMIT` (padrão 90). Sem as duas primeiras, em dev, o email (com o link) vai para o log; em produção (`COOKIE_SECURE=true`) a API não sobe sem elas, para o log nunca guardar links de cadastro e de recuperação. A conferência vem antes das migrations, como a do Redis: o deploy sem as variáveis falha sem mexer no banco, e a instância antiga segue no ar.
- **Onde fica**: `users.email`, nulo só na conta sem senha (a que entra só pelo Discord ou pelo Google). É da conta (contato e recuperação), não um login: o login por código, no futuro, usa o mesmo endereço. Só é gravado depois de confirmado pelo link, então todo email no banco foi confirmado e não há coluna de "verificado".
- **Forma canônica** (`mail/address.rs`, conferida também pelo check `users_email_format`): minúsculas; sem o `+etiqueta` em qualquer domínio (a mensagem para o endereço sem ela chega na mesma caixa); no Gmail, sem os pontos da parte local e `googlemail.com` vira `gmail.com`. É a forma gravada, mostrada e usada no envio (pedido do usuário: "salvos sempre como o slug"), e o `unique` da coluna barra o mesmo endereço escrito de outro jeito. Caractere que o provedor não tem é recusado, não removido: tirar o `_` de `joao_silva@gmail.com` apontaria para a caixa de outra pessoa. Formato aceito: só ASCII, parte local com letras, números, `.`, `_` e `-` (no Gmail, só letras e números), domínio com ponto e terminação só de letras (recusa IP e `localhost`). Fora disso, 422 `email.invalid`.
- **Domínios recusados** (422 `email.disposable`): a lista aberta disposable-email-domains (CC0, ~10 mil domínios, embutida no binário em `mail/disposable_domains.txt`, atualizada por `bun scripts/disposable-domains.ts`) e os serviços de apelido (DuckDuckGo, Firefox Relay, Apple, SimpleLogin, addy.io, Proton Pass, 33mail), que dão endereços sem fim para uma caixa e não estão naquela lista. Subdomínio de domínio recusado também cai. O que fica de fora, aceito: domínio próprio com catch-all e apelidos dentro do provedor (até 10 no Outlook, o "Ocultar meu email" do iCloud), que não dá para ver pelo endereço.
- **Cadastro com senha**: `POST /auth/signup` pede username, senha e email e responde 202 com o email canônico. A conta só nasce quando o link é aberto (`POST /auth/signup/confirm`, já com a sessão); até lá, tudo fica no Redis por 1 hora (pedido do usuário: cadastro que ninguém confirma não polui o banco):
  - `signup:{email}`: hash com username, hash argon2 da senha, idioma e o hash do token;
  - `signup_token:{hash}`: o email, lido com `GETDEL` (o link vale uma vez);
  - `signup_username:{username}`: o email que reservou o nome, para outro cadastro (e a criação ou troca de username de uma conta) não pegar o mesmo antes da confirmação (409 `auth.username_taken`).
  Um cadastro por email: pedir de novo troca o link e libera o username anterior. Username reservado pelo cadastro de outro email: quem o fez (a mesma senha, conferida contra o hash guardado) troca de email, e o cadastro anterior se desfaz, para um endereço digitado errado não prender o nome por 1 hora; com outra senha, 409. Email que já é de uma conta responde igual (202) e manda ao dono um aviso com o username e o caminho da recuperação, para o cadastro não revelar quem tem conta. Username já em uso continua respondendo 409, como antes.
- **Recuperação de senha**: `POST /auth/password/reset` com username ou email responde 202 sempre, e só manda o link se a conta tem senha e email; `POST /auth/password/reset/confirm` com o token e a senha nova troca a senha, encerra todas as sessões da conta, zera os erros de senha e entra numa sessão nova. Senha fora do formato não gasta o link.
- **Pôr ou trocar o email** da conta logada: `PUT /auth/email` manda o link ao endereço novo (o anterior vale até ele ser aberto) e pede a senha atual se a conta tem senha (quem pegou a sessão não troca o email para depois recuperar a senha por ele). `POST /auth/email/confirm` não exige login: o link prova que quem abriu recebe no endereço. Email de outra conta → 409 `auth.email_taken` (só para quem está logado e com a senha atual). Na conta, o campo já vem com o email de agora, e a senha atual só aparece quando ele muda.
- **Tirar o email**: `DELETE /auth/email`, só na conta sem senha (com senha, 409 `auth.password_needs_email`: remove-se a senha antes). Não pede senha, porque quem pode tirar já troca o email sem ela. Derruba o link de troca que estiver esperando, para um pedido antigo não pôr de volta um email que a pessoa tirou.
- **Links**: 1 hora, uso único, um vivo por conta e por tipo (o pedido novo derruba o anterior), só o hash do token no Redis (`password_reset:{hash}` e `email_change:{hash}`, com `…_user:{user_id}` apontando o último). O token (128 bits em base58, como o de convite) vai depois do `#` (`/{locale}/signup/confirm#…`, `/login/reset#…`, `/email/confirm#…`), que o navegador não manda a servidor nenhum. As páginas pedem um clique para confirmar: os scanners de link dos provedores abrem a página, e a confirmação automática criaria a sessão no robô.
- **Limites de envio** (`mail/kv.rs`): 60 s entre dois envios para o mesmo endereço (`email_cooldown:{endereço}`, 429 `email.too_soon` com os segundos) e um teto por dia em UTC (`email_sent:{dia}`, 503 `email.unavailable`), abaixo dos 100 do Resend. O envio é reservado antes de gerar o link, para um pedido recusado não derrubar o link que já foi. Na recuperação e no aviso de conta existente, fora dos limites o email só não sai, e a resposta é a mesma. Sem captcha por ora: um ataque pode gastar o teto do dia e mandar para endereços inexistentes (o que pesa na reputação do domínio); o Cloudflare Turnstile entra se acontecer.
- **Envio em segundo plano** (`tokio::spawn`): quem pede não espera o provedor, e a falha dele fica no log. Não passa pelo outbox, porque o token iria em claro para o banco.
- **Textos**: em `auth/emails/`, em português e espanhol (o idioma da conta; no cadastro, o da página), texto puro e HTML com o mesmo conteúdo. É a exceção à regra de a API devolver só códigos: o email sai da API, sem passar pelo front.
- **Visual** (desde 2026-10-29, pedido do usuário: "texto plano feio", seguir o Carbon): `mail/layout.rs` monta todo email igual, no visual do site. Cabeçalho de 48px com o nome do site (como o do UI Shell), bloco branco sobre `$layer-01` com título `heading-04`, parágrafos `body-02`, o aviso em destaque como a notificação de alerta de contraste baixo (`#fcf4d6` e borda esquerda `$support-warning`), um botão primário `lg` (texto à esquerda, folga à direita, sem canto arredondado), o endereço do botão por extenso para quem não consegue clicar e o rodapé `helper-text-01` com o nome do site e o endereço de quem recebe. Tabelas e estilo inline, porque é o que os leitores de email respeitam; o `g100` vale onde o leitor segue o modo escuro (Apple Mail, Outlook), por `prefers-color-scheme`. Fonte: a IBM Plex Sans de quem a tem instalada, com Helvetica e Arial no lugar; buscar no Google Fonts avisaria a terceiros cada abertura, e o Gmail ignora mesmo. Sem ícone, imagem nem pixel de abertura. Todo texto passa por escape no HTML, então parágrafo pode levar nome e endereço.
- **Avisos de segurança** (desde 2026-10-29, pedido do usuário: "email para cada ação importante na conta"): toda mudança de login ou de email manda um aviso ao email da conta (`auth/notify.rs`): senha criada, trocada (na conta ou pelo link de recuperação), removida; username trocado; Discord vinculado (com o nome dele no Discord) e desvinculado; Google vinculado (com o nome da conta Google) e desvinculado (o desvincular sem senha, que deixa a conta só no outro provedor, aponta para as sessões em vez da recuperação); email trocado (vai para o endereço de antes, com o novo por extenso) e removido (vai para o que saiu). Cada um diz o que mudou, "se foi você, não precisa fazer nada" e, em destaque, o primeiro passo de quem não fez, com o botão para ele: recuperar a senha quando quem mudou sabia a senha (a recuperação troca a senha e encerra todas as sessões), as sessões ou os logins nos outros casos. Escolhas minhas, fáceis de mudar:
  - Não avisam: nome exibido, encerrar sessões (só tira acesso), o primeiro email da conta (não há a quem avisar) e login novo, que gastaria o teto do dia (100 no plano grátis) a cada entrada.
  - Saem depois da mudança gravada, em segundo plano: a resposta não espera, e falha do Redis ou do provedor fica no log sem desfazer a mudança.
  - Contam no teto do dia, mas não usam nem marcam a espera de 60 s por endereço (`Mail::reserve_notice`): o aviso logo depois de um link (a senha trocada pelo link de recuperação) não se perde, e não atrasa o próximo link. O custo: quem tem a senha pode mandar avisos para si mesmo e gastar o teto do dia, como já poderia com cadastros para endereços próprios; limite por conta entra se acontecer. Fora do teto, o aviso só não sai.
  - Conta sem email (só Discord ou Google) não recebe aviso.
- **Exclusão da conta agendada** (desde 2026-10-28): o email da conta recebe a data e que entrar de novo cancela; dentro dos limites de envio, e fora deles a exclusão vale do mesmo jeito (ver "Excluir conta e excluir comunidade").

## Multi-tenant

- Um banco só, com coluna `tenant_id` em tudo o que pertence a um tenant.
- Toda função de acesso a dados de tenant recebe um `TenantId` tipado (extractor do Axum). Esquecer o filtro vira erro de compilação. RLS pode entrar depois como segunda camada.
- Tenant na URL por caminho: `/{locale}/{tenant}/...`.
- Papéis em `tenant_members`: owner, organizer, player.
- Na interface, tenant se chama **comunidade** (es: comunidad).
- Limite: cada usuário é owner de no máximo **3** tenants, fixo no código (`MAX_OWNED_TENANTS`). Ser organizer ou player em outros não conta.
- Slug: o front sugere a partir do nome, o usuário ajusta na criação e depois ele **não muda** (links de convite e de torneio nunca quebram). Formato a-z, 0-9 e hífen simples, de 3 a 32 caracteres, com uma lista de palavras reservadas para rotas do front (`new`, `invite`...).
- Um owner por tenant: quem criou, até transferir a posse. O banco garante exatamente um (ver "Consistência do banco").
- Convite: link **multiuso**, vale 7 dias, revogável. Owner e organizer geram; quem entra vira **player**. Só o hash do token fica no banco, então o link aparece uma vez, na criação. O link vai sem idioma (`/invite/{token}`) e o proxy do next-intl manda cada pessoa para o seu. O link de inscrição de um torneio (ver "Torneios") também faz entrar no tenant.
- Aceitar um convite sendo já membro não muda papel nem apelido. A prévia (`GET /invites/{token}`, pública) traz o slug da comunidade, o início do torneio no link de inscrição e, para quem está logado, se já é membro, se saiu (e o apelido de antes) e se já está inscrito: a tela troca o botão por "você já é membro" com o link da comunidade (ou do torneio, já inscrito); no link de inscrição de quem já é membro, o botão vira "Inscrever-se"; para quem saiu, diz que ele volta como jogador com o apelido e o histórico.
- Gestão de membros: o owner alterna player ↔ organizer, remove membros, transfere a posse e exclui a comunidade (agendada para 7 dias, só leitura até lá; ver "Excluir conta e excluir comunidade"); o organizer remove players; cada um sai sozinho.
- **Sair ou ser removido deixa o membro inativo, com o histórico** (`tenant_members.left_at`, e `removed_by` quando alguém removeu): a linha não é apagada (o banco nem deixaria, se ele jogou torneio iniciado). O inativo perde o acesso (a API responde como para quem é de fora: 404 `tenant.not_found`), some da lista de membros e de "Minhas comunidades" e não pode ser inscrito. Sai das inscrições dos torneios que não começaram (rascunho, inscrição, check-in), desiste dos em andamento em que está na chave (W.O. nas partidas pendentes, ver "Resultados") e, nos encerrados, fica como está. Os convites que ele criou são revogados (a FK composta só os apagaria com a linha). Nas chaves e listas de torneios iniciados o nome continua, com a marca "saiu".
- **Quem remove**: o owner remove qualquer um (menos ele mesmo); o organizer remove só players (organizer → 403 `tenant.forbidden`). Ninguém remove o owner (409 `member.is_owner`), e remover a si mesmo é 409 `member.remove_self` (sair é outra rota). Qualquer membro sai sozinho, menos o owner, que transfere a posse antes (409 `member.owner_must_transfer`). Rotas: `DELETE /tenants/{slug}/members/{user_id}` e `DELETE /tenants/{slug}/me`.
- **Remover não é banimento** (assumido): quem foi removido volta por qualquer convite válido. Para impedir, revogue os convites.
- **Voltar por convite reativa a mesma linha**: apelido e histórico de antes, **como player** (assumido, também para quem era organizer); `joined_at` continua o da primeira entrada e `invite_id` passa a ser o convite da volta (assumido). Vale para o link de inscrição de torneio também.
- **Desfazer o início** de um torneio tira as inscrições de quem saiu da comunidade ou desistiu (assumido): fora de andamento, inscrito inativo ou desistente não fica.
- **Transferir a posse** (`POST /tenants/{slug}/transfer-ownership` com `user_id` e `confirm_slug`): o owner escolhe um membro ativo (player ou organizer) e digita o slug da comunidade, que a API confere (422 `tenant.confirmation_mismatch`). O novo owner respeita o limite de 3 tenants como owner (409 `member.owner_limit_reached` `{max}`, contado com a linha do usuário travada, como na criação). O antigo owner vira **organizer**. Numa transação, rebaixa o owner atual antes de promover o novo (a ordem inversa bate no índice único).
- Página do tenant **só para membros**. Para quem é de fora, a API responde 404 `tenant.not_found`, o mesmo de um tenant inexistente, para não revelar que ele existe. A prévia do convite (`GET /invites/{token}`) é pública: ter o token já é o convite.
- Perfil por tenant: por enquanto só o **apelido** (`tenant_members.nickname`). Começa com o nome exibido do usuário (o do Discord ou o username do cadastro) e o próprio membro edita. **Pode repetir** dentro do tenant, sem tratamento (decidido junto com o check-in): as telas mostram o avatar ao lado, e as rotas identificam o membro pelo `user_id`.
- Configurações do tenant: os parâmetros do Elo (rating inicial e K), pelo owner (ver "Rating"). Ranking ligado/desligado, outro sistema (Glicko-2) e rating por modalidade ficam para quando houver o que escolher.

## Ids

- **Chave interna**: `bigint generated always as identity` (users, tenants, convites e o que vier). O Postgres é um só e gera os ids, então UUID/ULID não trazem vantagem. São 8 bytes contra 16, sequenciais (índice compacto, sem a fragmentação do UUID aleatório) e cabem no `number` do JS. `tenant_id` também é bigint: num índice composto com outro bigint, um `int4` não economiza nada por causa do alinhamento.
- **Não escondemos esses ids.** Toda rota que recebe um id confere a participação no tenant, então enumerar não dá acesso a nada; no máximo revela a ordem e o total aproximado de cadastros.
- **Tabela de ligação usa chave natural**: `tenant_members (tenant_id, user_id)`, `user_identities (provider, provider_user_id)`. Exceção: `participants` tem id próprio (bigint) além do `unique (tournament_id, user_id)`, porque ele vira o `ParticipantId` da chave (`engine::core::ParticipantId(i64)`; o `engine` não depende mais de `uuid`); nas rotas, o inscrito é identificado pelo `user_id`.
- **Identificador público e legível**: slug (tenant; torneio por tenant depois). Usuário não tem identificador público; se um dia tiver perfil público, ganha um handle.
- **Segredos** (sessão, convite, links por email): aleatórios, e só o SHA-256 fica guardado (o do convite no banco; o da sessão e os dos links, no Redis). O token de convite e o dos links por email têm 128 bits em base58 (22 caracteres, sem `0/O/I/l` e sem pontuação, então um duplo clique seleciona o token inteiro). O de sessão tem 256 bits em base64url (vive só no cookie).
- **Exceção: o começo do token de convite** (29/10, pedido do usuário). `tenant_invites.token_hint` guarda os 4 primeiros caracteres em claro, para a organização reconhecer o link na lista (`…/invite/7Fq2…`), saber qual revogar e ver por qual link cada membro entrou (`joined_via` na lista de membros, só para organizer e owner), caso um link vaze e vândalos comecem a entrar. Sobram ~105 bits desconhecidos (58^18), e o resto continua só como hash. Os links de antes não têm o começo e aparecem como "—" ou "link de convite".
- Se um dia houver ids gerados fora do banco ou bancos que se fundem: `uuidv7()`, nativo no PG18 (a ideia do ULID, com tipo nativo).

## Torneios

- Endereço `/{locale}/{tenant}/{torneio}`. O slug segue as regras do tenant (sugerido a partir do nome, ajustável na criação, a-z, 0-9 e hífen, de 3 a 32), é único dentro do tenant e **não muda**. Há palavras reservadas para as rotas do tenant (`new`, `members`, `settings`...).
- **Só membros** veem torneios. Quem é de fora recebe 404 `tenant.not_found`. Rascunho só aparece para organizer e owner; para player é 404 `tournament.not_found`.
- **Visibilidade**: público (padrão) ou privado. O público aparece para todos os membros; o privado, só para os inscritos, organizers e owner, e para os outros membros some da lista e responde 404 `tournament.not_found`, como se não existisse. Muda até o torneio encerrar.
- Organizer e owner criam e editam. **Criar já publica** (abre a inscrição; pedido do usuário em 28/10, para tirar um passo) ou, em "Criar como rascunho", gera um rascunho para publicar depois; só rascunho pode ser excluído. A criação recebe as traduções e o `publish` num POST só, numa transação: com erro, nada fica gravado (antes, criar e publicar em duas chamadas deixava o rascunho criado quando a publicação era recusada, e tentar de novo dava `tournament.slug_taken`). Erro de texto numa tradução volta com `params.locale`, o idioma dela.
- **Vagas obrigatórias** (2 a 1024). A checagem de campeões na criação usa o pior caso para esse número (o pior caso não diminui com mais participantes; há teste disso no `engine`) e roda de novo ao gerar a chave com os inscritos reais. As vagas também fecham a inscrição quando lotam.
- **Pool de campeões**: tabela global `champions` com os 17 atuais, e o pool do torneio é o conjunto ativo. Excluir campeões por torneio fica para depois.
- Bans de campeão por mapa: de 0 a 3, padrão 1.
- Não repetição na checagem: escopo partida (`match`, a série: entre os mapas de uma partida md3/md5) usa o maior melhor de N; fase, o pior caso da fase mais longa; torneio, a soma dos piores casos das fases. Sem a regra, basta sobrar um campeão depois dos bans.
- Formato padrão no formulário de duelo: eliminação dupla **sem** reset (pedido do usuário em 28/10), md3 nas partidas e md5 na grande final.
- **Não repetir campeão no formulário**: "pode repetir", "não repete na série" e "não repete no torneio". "Na fase" fica de fora enquanto o torneio tem uma fase só, porque até lá é igual a "no torneio" (a soma dos piores casos de uma fase é o pior caso dela); só aparece num torneio que já a tenha. Não existe "no mapa": no duelo cada jogador usa um campeão por mapa, então não há o que repetir dentro dele. Proibir os dois lados de usar o mesmo campeão no mesmo mapa (sem espelho) é outra regra, ainda não decidida.
- Edição: nome, descrição, regras, traduções e visibilidade até o torneio encerrar. Formato, vagas, regra de campeões, data de início e janela de check-in até ele começar; a checagem roda de novo a cada mudança e ao publicar. Vagas abaixo do número de inscritos são recusadas (`tournament.max_participants_below_registered`).
- **Data e hora de início** (`starts_at`, UTC). **Opcional em qualquer status** (pedido do usuário em 28/10): dá para publicar sem data e pôr, mudar ou tirar até o torneio começar. Sem data o check-in não abre sozinho (o organizador usa "abrir o check-in antes da hora"), não há aviso de hora de iniciar, e listas, cabeçalho e cartões mostram "sem data"; a lista de torneios continua por criação e "Seus torneios" ordena os sem data depois dos com data (assumido). Tirar a data com o check-in aberto não o fecha. O organizador digita no fuso dele (o navegador converte para UTC) e cada um vê no próprio fuso (formatado no navegador; no HTML do servidor sai em UTC até hidratar). Data no passado não é recusada: em vez disso, um **aviso** (não bloqueia) no formulário, na revisão antes de publicar, na aba de ciclo do rascunho e na confirmação de publicar, quando a data já passou ou está mais perto que a janela de check-in (o check-in abriria na hora e os jogadores não teriam tempo de se inscrever). É um componente só (`StartDateWarning`); sem data não há aviso. Publicar com o check-in já aberto continua levando direto ao check-in.
- **Check-in**: janela por torneio, em minutos antes do início (padrão 30; a API aceita de 5 a 1440 e o formulário oferece 15, 30, 45 e 60), ou **sem check-in**. Sem check-in não existe o status `check_in`: a inscrição vai direto para em andamento.
- **Ciclo depois de publicar**: inscrição → check-in → em andamento. O check-in **abre sozinho** quando chega `starts_at - janela`, avaliado pela API ao ler o torneio (lista ou página), sem job em segundo plano: a primeira leitura depois da hora grava a transição (com guarda contra mudança concorrente). O relógio fica na API, nunca no `engine`. Só anda para a frente: adiar o início com o check-in aberto não o fecha.
- O **início é sempre manual**: organizer ou owner clica em "Iniciar" a partir do check-in (ou da inscrição, sem check-in). O organizador também pode **abrir o check-in antes da hora**, **reabrir a inscrição** durante o check-in (os check-ins feitos continuam) e **desfazer o início** (volta para o check-in, ou para a inscrição sem check-in), para quando iniciou por engano. Desligar o check-in durante o check-in volta para a inscrição.
- **Reabrir a inscrição suspende a abertura automática** da janela que já tinha aberto: a API guarda quando reabriu (`registration_reopened_at`) e só reabre sozinha uma janela cuja abertura seja posterior a esse momento, ou seja, quando a data de início ou a janela mudam para depois. Assim a ordem entre reabrir e mudar a data não importa, e mudar a data só um pouco (para uma abertura que já tinha passado) não fecha a inscrição de novo na hora. A tela avisa que a automática está suspensa.
- **Check-in** se faz e desfaz só durante o check-in: o próprio inscrito, e organizer ou owner para qualquer inscrito (fica gravado quem marcou). Quem não fez continua inscrito (histórico), marcado sem check-in, mas fica fora do seeding e da chave. Inscrição manual pelo organizador durante o check-in entra **sem** check-in. Depois de iniciar, inscrições e check-ins congelam.
- **Seeding** na revisão antes de iniciar, só para organizer e owner: os elegíveis (com check-in; sem check-in no torneio, todos os inscritos) na ordem que vale. "Sortear" gera uma seed u64 aleatória na API, grava no torneio e embaralha pelo `engine` (`seeding::random_order`, ChaCha8 com a seed: a mesma seed e os mesmos elegíveis dão a mesma ordem em qualquer versão; um teste fixa o resultado). O ajuste manual manda a ordem completa de `user_id`s; ela precisa ter exatamente os elegíveis (`seeding.order_invalid` se alguém fez ou desfez check-in no meio). Seeds ficam em `participants.seed`.
- **Ao iniciar**: vale a ordem gravada; elegíveis sem seed vão para o fim, na ordem de inscrição; se ninguém tem seed, sorteia (e grava a seed). Os seeds são compactados para 1..N entre os elegíveis e os outros ficam sem. Mínimo de 2 elegíveis (`tournament.not_enough_eligible`). O seeding por rating é a ordem manual preenchida pelo rating (ver "Rating"): a organização ainda salva a ordem.
- **Inscrição**, por três caminhos, sempre de membros do tenant:
  - **botão**: o próprio membro, de qualquer papel (ver "Formatos"), só em torneio **público** e com a inscrição aberta; no privado, organizer e owner se inscrevem pela inserção manual;
  - **organizador**: organizer ou owner inscreve qualquer membro, em público ou privado, do rascunho até o torneio começar;
  - **link de inscrição**: o que um torneio privado usa para trazer gente, e também serve no público.
- Lotou, fecha (`tournament.full`). O inscrito sai sozinho enquanto a inscrição está aberta; depois disso, só o organizador tira, até o torneio começar. Inscrever de novo quem já está inscrito não dá erro.
- **Link de inscrição**: é um convite do tenant que também inscreve. Mesma tabela (`tenant_invites.tournament_id`), mesmo endereço (`/invite/{token}`), multiuso, revogável pela mesma rota. Não tem data: vale enquanto a inscrição estiver aberta e pode ser gerado já no rascunho, para mandar antes de publicar. Aceitar entra no tenant como player (quem já é membro mantém papel e apelido) e inscreve **numa transação só**: sem vaga ou fora da inscrição, não entra em nada.
- O idioma original não muda depois da criação. Tradução: uma por idioma diferente do original, com nome obrigatório; descrição ou regras vazias mostram as do original. A API devolve o original e as traduções, e o front escolhe pelo idioma de quem vê.
- Descrição e regras em **texto simples**: as quebras de linha e os recuos ficam (`UserText`, `white-space: pre-wrap`), nada é formatado (pedido do usuário em 28/10; o Markdown com `react-markdown` saiu).
- Erro com números sai como `{"error": "champions.pool_exhausted", "params": {"required": 32, "available": 17}}`, e o front interpola os números na tradução.

## Rating

- **Derivado, nunca editado direto**: reprocessar as partidas do tenant + ajustes manuais do organizador (com motivo e autor). Corrigir um resultado antigo → recalcular.
- Trait `RatingSystem` na crate `engine`. Elo primeiro.
- Rating único ou por modalidade (duelo, FFA, times), conforme a configuração do tenant.

Decidido pelo usuário em 28/10:

- **Elo por mapa**, rating inicial 1500: cada mapa confirmado de `match_games` é um jogo do rating, não a série. Os mapas sem nome nem frags (da conversão das séries antigas enviadas sem detalhe) contam igual, pelo vencedor. **W.O. não conta**, nem o do organizador nem o automático por desistência (não tem mapa); os mapas confirmados antes de um W.O. contam, porque foram jogados (assumido).
- **K decai com os mapas já computados da pessoa**: K = k_min + (k_max − k_min)·e^(−n/k_decay), com padrões 1500, 32, 80 e 10 (K = 32 + 48·e^(−n/10): 80 no primeiro mapa, ~50 no décimo, ~32 depois de uns 40). Configurável por comunidade.
- **Um ranking por comunidade**. Só existe duelo: rating único, com a coluna `modality` (só `duel`, ligada ao `mode` do torneio) nas tabelas, sem interface.
- **Ajuste manual** por organizer ou owner: pontos a mais ou a menos para um membro, motivo obrigatório, autor e horário gravados; entra no reprocessamento na ordem do horário.

Como ficou (assumido, fácil de mudar):

- **Derivado de verdade**: o rating é o resultado de reprocessar do zero, pelo `engine` (`rating::replay`), em ordem determinística, os mapas confirmados dos torneios que contam e os ajustes. Ordem: o horário em que o mapa confirmou (`confirmed_at`) ou o ajuste foi feito; no mesmo instante, mapas antes de ajustes; depois o id. `ratings` (rating, mapas, vitórias, derrotas, último mapa) e `rating_history` (o ± e o rating depois de cada evento, por pessoa) são cache, apagável e refeito. Correção, anulação, desfazer o início e reabertura mudam o passado e recalculam o tenant inteiro (centenas ou milhares de mapas: milissegundos).
- **Corrigir um mapa confirmado move ele para o fim da ordem**: a correção do `matches` grava `confirmed_at = now()`, então até mudar só os frags pode mexer 1 ou 2 pontos no rating de quem jogou depois. Manter o horário original na correção (no `matches`) resolveria; fica para quando incomodar.
- **Ratings inteiros**: cada variação é arredondada no evento (metade para longe do zero), para a soma dos ± exibidos bater com o rating. O vencedor ganha round(K_v·(1 − E_v)) e o perdedor perde round(K_p·(1 − E_v)): com o mesmo número de mapas (o mesmo K), o que um ganha o outro perde; novo contra veterano não é soma zero. Sem piso nem teto (as faixas são só do inicial). `exp` e `powf` são os da plataforma: um arredondamento caído a ~1e-13 da metade poderia diferir entre Windows e Linux; um teste fixa valores para pegar isso.
- **Faixas da configuração**: inicial 100–3000, K mínimo 1–100, K máximo 1–200 e não abaixo do mínimo (igual: K fixo), decaimento 1–100 mapas (no `engine`, repetidas como `check` na tabela). **Só o owner muda**, na aba Configurações, como as outras decisões da comunidade inteira (transferir a posse); todos leem. Mudar recalcula o histórico inteiro na hora.
- **Ajuste**: de −1000 a 1000 pontos, sem zero, para membro ativo; motivo de 1 a 280 caracteres; não conta como mapa (não muda o K). Não se apaga nem se edita: corrige-se com outro ajuste, e a lista é o histórico. A lista (com motivo e autor) é só da organização; os outros veem a soma dos ajustes no resumo, para o número se explicar sem expor o motivo.
- **Recálculo sem chamada nova no `matches`**: um trigger no banco grava uma marca em `rating_dirty` quando muda um mapa confirmado, um ajuste, a configuração ou o "conta para o rating" (mapa pendente, contestado ou anulado sem ter confirmado não marca). A marca é uma linha nova, nunca o update de uma linha por tenant: quem grava um mapa não espera ninguém. Recalculam o agendador (a cada 10 s, depois das confirmações por tempo, um tenant por transação), a leitura do ranking e do rating de um membro (antes de ler, se há marca) e as rotas de ajuste e de configuração (na própria transação). O recálculo trava o tenant (advisory lock), apaga as marcas que vê e só depois lê o histórico; a marca de uma transação que ainda não confirmou fica e faz recalcular de novo. Se o cache sai igual, não grava nem emite; se muda, emite `tenants::changed`.
- **Custo no Redis**: cada mudança do ranking recarrega as páginas abertas da comunidade e dos torneios dela (uma leitura de sessão cada). O agendador junta as mudanças de 10 s, e um mapa confirmado costuma dar uma recarga pela partida e outra, até 10 s depois, pelo ranking. Se pesar, um evento próprio do ranking (só a aba Ranking, a pessoa e o seeding) evita a segunda.
- **Cache sem FK para o mapa e o ajuste**: `rating_history.game_id` e `adjustment_id` não têm FK de propósito (a FK travaria o mapa contra o recálculo: anular um mapa enquanto o histórico é regravado dava deadlock). O que some marca o tenant, recalculado antes da próxima leitura.
- **Torneio "conta para o rating"**: padrão sim, também para os que já existiam; no grupo Formato do formulário, muda até o torneio começar (`tournament.setup_locked` depois). O resumo do formato diz se conta.
- **Quem vê**: todos os membros veem o ranking e o rating de cada um. Na página da pessoa, o resumo (rating, posição, mapas, V–D, último mapa, soma dos ajustes) e os últimos 20 mapas que contaram (torneio, adversário, mapa, resultado, ±, rating depois), só dos torneios que quem vê vê na lista da comunidade (privado sem inscrição: o rating aparece, os mapas não).
- **Ranking**: só membros ativos com algum mapa ou ajuste. Quem saiu some do ranking, mas os mapas dele continuam no rating dos outros. Ordem: rating, depois mais mapas, depois apelido; empatados no rating dividem a posição (1, 2, 2, 4). Menos de 10 mapas = **provisório**, marcado na lista e na página da pessoa.
- **Seeding por rating**: na página de seeding, cada linha mostra o rating, e "Ordenar por rating" preenche a ordem na tela (maior rating primeiro; sem rating no fim, na ordem em que estavam; empate também na ordem em que estavam). A organização ainda salva pela rota da ordem manual.
- **Os ratings de quem já jogou** aparecem na primeira passada do agendador depois do deploy: a migration marca todos os tenants.

## i18n

- A API devolve **códigos** (`match.already_reported`), nunca texto. Status, formatos e fases são enums no código, traduzidos no front.
- Datas em UTC no banco, exibidas no fuso de quem vê.
- Conteúdo do organizador: idioma original + traduções **opcionais** em `tournament_translations (tournament_id, locale, ...)`. Sem tradução, mostra o original.
- **Trocar o idioma**: seletor no cabeçalho, que mantém a página; cada idioma aparece no próprio nome ("Español" também para quem lê em português).
- **Espanhol**: a chave do torneio é sempre **llave** (llave de ganadores, llave de perdedores), mais comum na Argentina que "cuadro" (assumido; antes as duas palavras se misturavam).

## Formatos

- Dois eixos independentes:
  - **chaveamento**: eliminação simples, dupla, round robin, suíço, lobbies FFA, série de pontos;
  - **partida**: melhor de N mapas; no FFA, pontos por colocação **ou** soma de frags (configurável).
- Duelo, 2v2 e 3v3 são o mesmo motor com `team_size` diferente.
- O torneio tem **fases** (`stages`) no modelo desde o início; a interface pode começar com uma.
- Fluxo: inscrição individual → check-in (janela antes de começar; quem não fizer fica fora da chave) → formação de times → seeding → chave. Detalhes do check-in e do seeding em "Torneios".
- Qualquer membro do tenant se inscreve, inclusive organizer e owner: os papéis são cumulativos (organizer também é jogador), então a rota usa `TenantMember<Player>`.
- Times são por torneio, montados pelo organizador: sorteio aleatório, sorteio balanceado por rating (zigue-zague) ou manual (arrastar). O capitão é definido pelo organizador ou pelo sorteio.
- Seeding: manual, aleatório (seed salva) ou por rating (a ordem manual preenchida pelo rating da comunidade).
- Toda aleatoriedade (sorteios, timeouts) recebe uma seed ou RNG por parâmetro e a seed é salva, para que o resultado seja reproduzível e auditável.

## Veto e campeões

- Veto de mapas ao vivo, em turnos, com cronômetro. O capitão faz o veto.
- Ban de campeão pelo capitão; pick de campeão por cada jogador.
- Timeout: ban ou pick aleatório; o organizador pode desfazer.
- Pools de mapas e campeões são tabelas, não constantes. Campeão novo no jogo = linha nova.
- Regra de não repetição **opcional**, configurável em dois eixos: quem (jogador | time) × escopo (partida | fase | torneio).
- Validação na criação: pior caso de jogos por participante comparado com o pool menos os bans. Se faltar campeão, bloqueia com mensagem com números ("no pior caso são necessários 24 campeões; o pool tem 17").

## Resultados

- Um lado envia o resultado; os demais têm uma janela para contestar. Sem contestação, confirma. Contestação vai para o organizador. Vale para duelo, times e FFA. No duelo (e nos times), **cada mapa da série é enviado e confirmado sozinho** (pedido do usuário em 28/10: a série inteira de uma vez era ruim de usar).
- **A chave nasce no "Iniciar"**, na mesma transação: `TournamentSetup::validate` roda de novo com o número real de elegíveis e o pool de campeões de agora (`champions.pool_exhausted` com os números se faltar), e a chave é montada com os elegíveis na ordem dos seeds. **Nada do estado do `engine` é gravado**: ficam a configuração (`tournament_stages`), os participantes (seeds 1..N) e os resultados (`match_results`); a chave é sempre refeita por `replay` com os confirmados na ordem em que passaram a valer (`position`, mantida nas correções), e cada resultado também guarda os lados com que entrou, conferidos no replay.
- **Uma fase por enquanto**: os resultados já têm `stage`; uma fase seguinte teria como participantes a classificação da anterior, montada quando ela termina (`matches/stage.rs`).
- **Identificador de partida** nas rotas e no banco: o `MatchId` legível, `wb-1-3` (chave de cima; na simples, tudo é `wb`), `lb-2-1` (de baixo), `gf-1-1` e `gf-2-1` (grande final e reset). Rotas `.../bracket` e `.../matches/{partida}`; chave e partidas seguem a visibilidade do torneio.
- **Envio, mapa a mapa**: qualquer um dos dois jogadores de uma partida pronta envia o mapa N (`POST .../matches/{partida}/games/{n}/report`): quem venceu (pelo lado), o mapa jogado (um mapa ativo, obrigatório para o jogador) e os frags de cada lado (opcionais, os dois ou nenhum, de 0 a 999, sem empate e com mais frags para quem venceu). O número vai no caminho, para dois envios simultâneos do mesmo mapa não virarem dois mapas (`match.game_already_reported`). Quem não joga não envia (`match.not_player`); o organizador que não joga lança.
- **Regras da série** (do `engine`, `series::games`; a API só carrega, chama e grava):
  - o mapa N+1 exige o N **enviado**, não confirmado (`match.game_out_of_order` `{next}`); quem enviou um mapa já pode mandar o próximo;
  - o mapa não se repete na série (`match.map_repeated`), até o veto existir;
  - **não há mapa depois da decisão**: o próximo é recusado quando os mapas enviados e não contestados já dão a maioria a alguém (`match.series_decided`, inclusive com eles ainda pendentes) ou quando a série já teve os N mapas (`match.no_games_left`);
  - **mapa contestado não conta** para essa decisão (o vencedor dele está em dúvida), então contestar o mapa N não trava o N+1, nem quando o contestado decidiria a série: se os jogadores jogaram o mapa seguinte, é porque o resultado contestado provavelmente estava errado;
  - quando a contestação se resolve (ou o organizador corrige um mapa), os mapas que passam a ficar depois da decisão são **anulados** (apagados, com o evento `voided` no histórico). Assumido: o organizador decidiu o mapa, então o seguinte não existiria; o rules-reviewer sugeriu segurar o próximo mapa quando o contestado decidiria a série, recusado porque travaria o caso comum (o adversário contesta porque ele venceu e os dois seguem jogando);
  - **a série fecha sozinha** quando os mapas confirmados, em sequência desde o primeiro, dão a maioria (2 na md3, 3 na md5): todos os mapas até o que deu a maioria precisam estar confirmados (um contestado no meio segura a série, porque o placar ainda pode mudar). Só então a série entra em `match_results` (`confirmed_via = maps`, com o placar dos mapas e o horário da confirmação que faltava) e a chave avança pelo `replay`, como antes; o evento `decided` registra o placar.
- **Resposta, por mapa**: o adversário confirma ou contesta cada mapa com um comentário (1 a 280 caracteres); contestado sai da janela e espera o organizador. Quem enviou não confirma nem contesta o próprio mapa.
- **Janela de contestação**: por torneio, padrão **10 minutos** (era 5; os torneios que ainda não tinham começado e estavam com 5, o padrão antigo, passaram para 10 na migration `20261101000000_contest_window`; os já iniciados ficaram como estavam), a API aceita de 1 a 1440 e o formulário oferece 2, 5, 10, 15, 30 e 60. Vale **por mapa**: muda até o torneio encerrar e vale para os envios seguintes (o prazo fica gravado em cada mapa). Sem resposta, o mapa confirma sozinho no fim da janela, avaliado pela API ao ler a chave ou a partida e antes de cada ação (como a abertura do check-in, sem job; só trava o torneio quando há prazo vencido). `matches::due::apply_due_confirmations` é a peça isolada que o agendador do tempo real vai chamar.
- **A chave só avança com a série decidida** (pelos mapas confirmados, por W.O. do organizador ou pelo W.O. automático). Antes disso, a próxima partida continua esperando; a chave mostra o placar dos mapas confirmados e quando há mapa esperando confirmação ou contestado.
- **Organizador** (organizer ou owner, **inclusive em partida que ele joga**; tudo fica no histórico com autor e horário): **confirma na hora** um mapa pendente (quando o adversário demora), resolve a contestação de um mapa (aceitando como foi enviado, ou com outro resultado), **lança** o próximo mapa e **corrige** qualquer mapa (`PUT .../games/{n}`, já confirmado), também com o torneio encerrado, dá **W.O. na série inteira** (`PUT .../result`; só ele dá) e **anula um mapa para ser jogado de novo** (`POST .../games/{n}/replay`, com nota opcional; pedido do usuário em 28/10, para a queda no meio do mapa e a revanche combinada entre os dois). Anular vale para o **último mapa da série, pendente ou contestado**: ele sai (evento `replay` no histórico, com autor e nota) e o mesmo número volta a poder ser enviado pelos jogadores, com a janela de contestação de sempre. Confirmado não se anula (corrige-se), e um do meio é recusado (`match.game_not_last {last}`), para a numeração não ficar com buraco; anula-se do fim para o começo. No W.O., os mapas confirmados ficam (foram jogados) e os pendentes e contestados são anulados. A correção de um mapa refaz a série: se a série decidida muda de vencedor ou placar, a chave é refeita por `replay` com a série nova na mesma posição; se fica sem decisão (ex.: 2 x 0 vira 1 x 1), a série **reabre** (evento `reopened`) e a chave volta a esperar. A correção é recusada (`match.correction_conflicts`) se uma partida decidida depois deixa de fechar (vencedor que não chega lá, outros lados, reset que deixa de existir), e os mapas de partidas ainda abertas cujos lados mudaram são anulados (evento `voided`). Mapas que os mapas confirmados decidem por cima de um W.O. (o organizador lança o que faltava) substituem o W.O.
- **Fim**: quando a decisiva é confirmada (final da simples; grande final sem reset necessário, ou o reset), o torneio vira `finished` sozinho e mostra a classificação (`Placement`). Uma correção que volta a deixar partida por jogar (ex.: o reset passa a ser necessário) devolve o torneio para `in_progress`.
- **Desfazer o início** é permitido com resultados e apaga séries, mapas e histórico; a chave informa quantas partidas têm mapa ou resultado e a tela pede, havendo algum, que se digite o endereço do torneio. Só em andamento: depois de encerrado não se desfaz (assumido; a correção continua valendo).
- **Histórico** por partida (`match_events`): os eventos de um mapa levam o número dele (`game`) e o vencedor do mapa (enviado, confirmado, confirmado por tempo, contestado com o comentário, resolvido, lançado, corrigido, anulado); os da série, o vencedor e o placar (série decidida, reaberta, W.O., W.O. automático). Com autor, horário e nota opcional do organizador. Os eventos de antes do envio mapa a mapa ficam como eram (da série inteira). Só desfazer o início apaga.
- **Desistência**: num torneio em andamento, o inscrito da chave desiste quando o organizador marca (`POST .../participants/{user_id}/withdrawal`, botão "Desistência" na página do torneio) ou quando sai (ou é removido) da comunidade. Fica em `participants.withdrawn_at` (e `withdrawn_by`, o organizador ou quem removeu). Ele continua na chave e na lista, com a marca "desistiu" (ou "saiu"), e na comunidade, se foi só desistência. **Não se desfaz** (assumido; o organizador ainda corrige resultados). Marcar de novo não dá erro; inscrito fora da chave (sem seed) não desiste (409 `participant.not_in_bracket`). As confirmações por tempo vencidas valem antes.
- **W.O. automático**: toda partida pronta com um lado fora (desistiu ou saiu da comunidade) vira W.O. para o adversário, confirmado "pela desistência" (`confirmed_via = withdrawal`), sem autor, com o evento `auto_walkover`. É aplicado depois de toda mudança que pode deixar partida pronta (confirmação pelo adversário, pelo organizador ou por tempo, resolução, lançamento, correção, W.O. e a própria desistência), repetindo até não sobrar nenhuma: na dupla, quem perde por W.O. na chave de cima cai na de baixo e leva outro W.O. quando aquela partida ficar pronta. Assim nenhuma partida pronta fica esperando quem saiu, e ler a chave não precisa aplicar nada.
- **Mapa pendente ou contestado** na partida pronta de quem desiste é anulado, e a série vira W.O. para o adversário; os mapas confirmados ficam (assumido: quem desistiu não jogaria o resto de qualquer forma).
- **Os dois lados fora**: W.O. para o seed melhor (assumido); na dupla, ele cai na partida seguinte e a regra vale de novo.
- Quem sai da comunidade com o torneio já encerrado não é marcado desistente, mas conta como fora se uma correção reabrir o torneio.
- **Mapas**: tabela global `maps` (como `champions`), com `duel_pool`. Lista **provisória, para o usuário revisar**: pool de duelo = Awoken, Blood Covenant, Blood Run, Corrupted Keep, Deep Embrace, Exile, Insomnia, Molten Falls, Ruins of Sarnath, Vale of Pnath; fora do pool = Burial Chamber, Church of Azathoth, Lockbox, Tempest Shrine, The Longest Yard, Tower of Koth. Nome de mapa é nome próprio (não se traduz). `GET /maps` é pública. Até o veto definir um pool por torneio, o envio aceita qualquer mapa ativo, sem repetir na série (o formulário mostra o pool de duelo primeiro).
- **Rating por mapa** (ver "Rating"): por isso cada mapa é uma linha de `match_games`, com o vencedor, o mapa e os frags.
- **Conversão das séries enviadas inteiras** (migration `20261101010000_games`, determinística): cada série com placar virou um mapa por mapa jogado. Com detalhe, cada mapa veio do detalhe (o vencedor é quem fez mais frags). **Sem detalhe, os mapas ficaram sem nome nem frags** (`map_id` nulo, permitido só para eles: o jogador sempre informa o mapa; o organizador pode manter sem ao corrigir), primeiro os do perdedor e depois os do vencedor, para o último ser de quem venceu. Cada mapa herdou o estado e a autoria do envio da série (quem enviou e quando, prazo, contestação com o comentário em todos os mapas da série contestada, confirmação). A série pendente ou contestada saiu de `match_results`: fecha quando os mapas confirmarem (pelo prazo que já tinham, ou pelo organizador). W.O. não tem mapas.
- **Banco rigoroso**: as invariantes também estão no banco. `match_games`: vencedor entre os lados, frags com mapa, sem empate e batendo com o vencedor, mapa sem repetir na série, envio de jogador com lado e prazo, contestado com comentário, confirmado com via e horário; no commit, os mapas de uma partida têm os mesmos lados e números de 1 a n (`match_games_sequence`). `match_results` só guarda a série decidida (`match_results_decided`); com ela, todos os mapas da partida estão confirmados e com os lados dela (`match_games_series_decided`) e o placar dela, fora o W.O., é o dos mapas (`match_results_games_score`). As FKs são compostas pelo torneio (participante do mesmo torneio, torneio do mesmo tenant) e participante ou fase de torneio iniciado não sai avulso (ver "Consistência do banco").
- Print do placar: o torneio decide se é obrigatório.
- Upload direto do navegador para o bucket, com URL assinada gerada pela API. O front converte para WebP antes.
- Prints apagados 30 dias após o fim do torneio (rotina diária).
- **Bucket na AWS S3, classe Standard** (28/10). Express One Zone custa quase 5 vezes o Standard e só ganha latência para máquina na mesma zona da AWS (a API está no Render). One Zone-IA economiza centavos e cobra leitura, mínimo de 30 dias e 128 KB por arquivo, além de exigir a classe assinada no upload.
- **Sem CloudFront por enquanto**: os prints seguem a visibilidade do tenant e do torneio, e a URL assinada de leitura do S3 expira sozinha; no CloudFront isso pediria URL assinada própria (outro par de chaves). Os 100 GB de saída grátis por mês da AWS bastam. A API devolve a URL de cada print (o front não monta endereço do bucket), para o CloudFront poder entrar depois só no backend.

## Consistência do banco

- O banco recusa estado inválido e entidade órfã mesmo que a API erre; a API continua conferindo antes, para devolver o código certo. Regras nas migrations `20261030000000_delete_rules` e `20261030010000_consistency_checks`, testes em `tests/api/schema/`, checklist para migration nova no `backend/CLAUDE.md`.
- **Excluir usuário** é recusado se ele for owner de algum tenant ou tiver participado de torneio iniciado (em andamento ou encerrado), para a chave antiga não perder um lado. Os logins vão junto; as sessões dele, no Redis, ficam sem efeito até expirar, e as tentativas de senha expiram com a janela. A autoria (quem inscreveu, marcou o check-in, enviou, contestou ou confirmou um resultado, agiu no histórico) fica nula. Os convites que ele criou saem com a participação dele no tenant: convite é uma autorização dada pelo membro.
- **"Excluir conta"** **anonimiza** o usuário (nome, avatar, email, logins, sessões, inscrições de push) em vez de apagar a linha, para os torneios que ele jogou continuarem inteiros; regras e forma no banco em "Excluir conta e excluir comunidade".
- **Excluir tenant** apaga tudo o que está dentro (pela API, agendado para 7 dias: ver "Excluir conta e excluir comunidade"). **Excluir torneio** também, inclusive resultados, mapas e histórico (a API só exclui rascunho, mas o banco aceita qualquer um).
- **Inscrito e fase de torneio iniciado** não saem avulsos, só com o torneio ou o tenant; também ninguém entra e seed e check-in não mudam. Por isso o membro inscrito num torneio iniciado também não sai do tenant: sair mantendo o histórico é ficar inativo, não linha apagada.
- **Membro inativo** (migration `20261031000000_inactive_members`): o owner nunca fica inativo; `removed_by` só em quem saiu, nunca ele mesmo, e fica nulo se o autor for apagado; sair exige os convites dele revogados e nenhuma inscrição em torneio que não começou; inativo não cria nem reabre convite e não é inscrito; torneio que volta a não ter começado (desfazer o início) não fica, no commit, com inscrito inativo.
- **Desistência e W.O. automático** (migration `20261031010000_withdrawals`): desistência só com o torneio em andamento, só de quem tem seed, e não se desfaz nem muda de data; torneio que volta a não ter começado não fica com desistente. O W.O. automático não tem placar, nem quem enviou, nem quem confirmou, e o perdedor desistiu ou saiu da comunidade; o evento `auto_walkover` tem só o vencedor e nenhum autor. Os checks trocados de `match_results` e `match_events` (eram `match_results_check6` e `match_events_check2`, nomes gerados pelo Postgres) ganharam nomes explícitos.
- **Owner**: exatamente um por tenant, e ele é membro. "No máximo um" vale na hora (índice único parcial); "pelo menos um", no commit. Transferir a posse é, numa transação, rebaixar o owner atual e depois promover o novo (na ordem inversa, o índice recusa).
- Quem inscreveu, quem marcou o check-in e quem criou o convite são membros do mesmo tenant (FK composta); o convite gravado numa inscrição é um link do mesmo torneio.
- **Estado e forma também no banco**: status check-in só com janela; tradução nunca no idioma original; ao menos uma fase por torneio; vagas nunca abaixo dos inscritos; slug do tenant e slug, tenant e idioma original do torneio fixos; JSON de regras de campeões e de fase com a forma do `engine` (bans de 0 a 3, melhor de N ímpar); username no formato do cadastro, senha só como hash argon2id, tokens como SHA-256 de 32 bytes, avatar só por https, nome exibido não vazio, campeão com nome único.
- Torneios publicados antes de existir a data de início ganharam a data de criação, e os que estavam na inscrição ficaram com a abertura automática do check-in suspensa (como numa reabertura), para não mudarem de status sozinhos.
- A regra do banco `tournaments_starts_at_required` (data fora do rascunho) foi removida pela migration `20261115000000_starts_at_optional` quando a data virou opcional; o código `tournament.starts_at_required` deixou de existir.
- **Fica fora do banco, de propósito**: ordem entre horários de ações de transações diferentes (cada uma grava o próprio `now()`, e uma pode ter começado antes da outra); validade de convite posterior à criação e histórico imutável (os testes envelhecem essas datas direto no banco); o limite de 3 tenants por owner e o pool de campeões (regras da API, que mudam sem migration).

## Excluir conta e excluir comunidade

Owner → 409 `auth.owns_tenants`; a regra é do banco (`users_deletion_owner`), conferida com a linha do usuário travada (como criar comunidade e transferir a posse), e no outro sentido ninguém vira owner com a exclusão agendada (`tenant_members_owner_deleting`; na transferência, 409 `member.deletion_scheduled`) (assumido).

A tela vai para a página de entrar, com a data e o formulário logo embaixo.

**Comunidade**
- `POST /tenants/{slug}/deletion` (owner, com `confirm_slug`) grava `tenants.deletion_due_at` (agora + 7 dias) e `deletion_requested_by`; `DELETE` cancela. Quem pediu é sempre o owner atual (`tenants_deletion_by_owner`, no commit, e FK para `tenant_members`).

Fora do extractor (assumido): a prévia e o aceite de convites e links de inscrição respondem o mesmo código; o agendador não abre o check-in nem avisa a hora de iniciar (nem a abertura ao ler), e o que venceu nesse meio-tempo acontece na primeira passada depois de cancelar. A confirmação por tempo não tem o que fazer: não há torneio em andamento.
- Recusada com torneio em andamento, 409 `tenant.tournament_in_progress` (assumido): só leitura congelaria a partida no meio, então o owner encerra o torneio ou desfaz o início antes. No banco, nos dois sentidos: não agenda com torneio em andamento (`tenants_deletion_in_progress`) e torneio não começa com a exclusão agendada (`tournaments_tenant_deleting`, que trava a linha do tenant).
- Os membros veem o aviso com a data no topo da comunidade (o owner, com o caminho para cancelar nas configurações, onde a transferência de posse some até lá), e as páginas recarregam ao agendar e ao cancelar (`tenants::changed`) (assumido). Sem aviso por push nem email.
- Na data, o agendador apaga o tenant, um por transação, e a cascata leva tudo o que está dentro; antes, cada membro ativo recebe `access_lost`, como quem é removido (assumido). Os prints no bucket saem pela fila do domínio de prints, que um trigger enche quando a linha do print sai.
- A data agendada no futuro não é conferida no banco (ver "Fica fora do banco"): cada transação grava o próprio `now()`.

## Interface

Decididas na revisão de uso de 28/10 (todas assumidas, sem rodada de perguntas; design por utilidade, sem enfeite).

- **Home**: sem login, diz o que fazer (entrar ou criar conta; link de convite leva ao cadastro). Logado, as pendências da organização (para quem organiza e tem alguma), "Seus torneios" e depois "Minhas comunidades". O status da API só aparece quando há problema.
- **Seus torneios** (rodada 2b, `GET /me/tournaments`): os torneios em que a pessoa está inscrita, de todas as comunidades, cada um com a **situação** dela (inscrição feita, check-in pendente ou feito, fora da chave sem check-in, na chave, terminou em Nº, desistiu, 1º lugar) e, para quem ainda joga, a **próxima partida** como link, com o adversário (ou "quem vencer C1.2") e o que ela espera (enviar o mapa, confirmar ou contestar, aguardar). Os que não encerraram vêm primeiro (em andamento, check-in, inscrição; pelo início); os **encerrados** ficam numa lista à parte, menor, só com os 5 de início mais recente (assumido: cada um refaz a chave para dar a colocação, e a lista inteira cresceria sem fim). As confirmações por tempo vencidas valem antes, como ao abrir a chave. A situação é uma etiqueta (destaque para o check-in que falta) e a próxima partida fica fora do link do torneio, para não haver link dentro de link.
- **Pendências da organização** (28/10, `GET /me/organizing`; assumido, fácil de mudar): na home, acima de "Seus torneios", para quem é organizer ou owner ativo em alguma comunidade, o que espera a organização em todas elas, em tiles que levam aonde se resolve. **Mapa contestado** (torneio, comunidade, partida e mapa, quem contestou e há quanto tempo; leva à partida) e **hora de iniciar** (torneio na inscrição ou no check-in com o início marcado já passado, o critério do aviso `tournament.start_due` sem o "uma vez": fica na lista até iniciar ou adiar; o início marcado e quantos fizeram check-in, ou quantos se inscreveram quando não há check-in; leva à aba Organização). Os contestados vêm primeiro (há uma partida parada), do mais antigo; depois os torneios, do início mais antigo. Organizer e owner veem todos os torneios da comunidade, então o papel basta como filtro.
  - **Sem pendência, o bloco some** (também para quem organiza): o aviso com som e o push já chamam quando chega algo, e um "nada a resolver" no topo da home de todo organizador empurraria "Seus torneios" para baixo sem dizer nada útil.
  - **Ficaram de fora**: mapa pendente com prazo longo e adversário sumido (confirma sozinho no fim da janela, e "confirmar agora" na partida já resolve; não pede ação da organização) e torneio com check-in aberto antes da hora (vira pendência quando a hora chega; como informação, a home da organização recarregaria a cada check-in).
  - **Rota própria, não um campo de `/me/tournaments`**: aquela devolve uma lista (virar objeto mudaria quem a usa) e refaz a chave de cada torneio, enquanto as pendências saem de duas queries que leem direto as tabelas. E só quem organiza pergunta: o front decide pelos papéis de "Minhas comunidades", que a home já busca, então quem só joga não gasta uma leitura de sessão a mais no Redis a cada recarga.
- **Página da comunidade**: torneios, membros, convites e, por último, "Você nesta comunidade" (apelido e sair, ou transferir a posse).
- **Página do torneio**, de cima para baixo: para a organização, um quadro só com o estado, o próximo passo (publicar, abrir o check-in, iniciar, desfazer) e editar; depois a inscrição e o check-in de quem vê (inclusive o aviso de quem ficou fora da chave sem check-in); "Partidas que esperam você" (enviar, responder, resolver) com link; a chave, que ocupa a largura à direita da coluna de texto; descrição, formato, seeding, inscritos, links de inscrição e regras. Encerrado, "Editar" some (nada mais muda).
- **Partida** (refeita para o envio mapa a mapa): o código curto (C2.1) aparece logo abaixo do título, como no cartão da chave; no topo, o placar da série (o dos mapas confirmados enquanto ela corre, com quantos mapas vencem e quantos esperam confirmação ou estão contestados). Depois, **uma linha por mapa**, com o mapa, quem venceu e os frags, uma etiqueta de estado (aguardando, contestado, confirmado) e a frase do estado: até que horas confirma sozinho, com a contagem; contestado por quem e o comentário; confirmado e como. Sem confirmar, o mapa aparece como **o que quem enviou diz** ("X enviou: Y venceu", sem negrito) e a frase diz que ele ainda não conta no placar (pedido do usuário em 28/10: o negrito em "Y venceu" ao lado do 0 × 0 do placar parecia fato). Confirmar e contestar ficam na linha do mapa; para a organização, "confirmar agora", "confirmar vitória de X" (no contestado, para dizer o efeito), "lançar outro resultado"/"corrigir" (o formulário abre na própria linha) e, no último mapa sem confirmar, "anular: jogam de novo", que abre a explicação e a nota antes de anular. As janelas aparecem em horas quando passam de 60 minutos ("24 h", não "1440 min"). O **próximo mapa** é a última linha: para quem joga, o formulário aberto (vencedor com os dois nomes como botões de opção lado a lado, o mapa e os frags opcionais); para a organização que não joga, "lançar mapa N" fechado atrás de um botão. O W.O. na série fica no quadro da organização, fechado.
- **Iniciar com a conta** (rodada 2b): a confirmação de "Iniciar torneio" diz quantos entram na chave e, no check-in, quantos ficam de fora sem check-in. Com menos de 2 elegíveis (o mínimo da API), o botão fica desabilitado e o motivo aparece embaixo, em vez de deixar clicar para receber o erro.
- **Correção recusada, explicada antes** (rodada 2b): numa série decidida cujo vencedor ou perdedor já jogou uma partida seguinte também decidida, a organização vê, abaixo dos mapas, por que mudar o resultado desta série é recusado (`match.correction_conflicts`: a partida seguinte foi jogada com os lados que ele definiu) e o que fazer: corrigir antes a seguinte até ela ficar sem decisão (começando pela última, se houver uma cadeia) e voltar; os mapas dela são anulados quando os lados mudam. Corrigir mapa e frags sem mudar o resultado continua valendo. Se a seguinte foi decidida por W.O., a nota diz que ela não volta a ficar sem decisão e só desfazer o início resolve. O erro da API, se ainda assim tentar, diz o mesmo. A regra não mudou.
- **Publicar pede confirmação**: publicado, o torneio não volta a rascunho nem pode ser excluído.
- **Seeding**, na interface **"Ordem da chave"** (29/10: "seeding" sozinho não diz nada a quem não organiza torneios), com a explicação de que os de cima pegam os de baixo na primeira rodada e os dois primeiros só se cruzam no fim: o título diz quantos inscritos entram na chave (no check-in, quantos fizeram); sem seed nenhum, a lista avisa que a ordem mostrada não vale até salvar (iniciar assim sorteia). A posição de cada um é um campo numérico (rodada 2b): digitar o número e dar Enter (ou sair do campo) leva direto para lá, os outros descem um; as setas continuam para o ajuste fino. Com Enter, o foco fica no campo na posição nova, para quem usa o teclado. Arrastar ficou de fora: no celular, arrastar numa lista que rola é impreciso.
- **Confirmação na própria tela, não `confirm()`** (rodada 2a de UX, 28/10): o botão vira a pergunta com o que vai acontecer, "sim" com o mesmo texto do botão e "Não" (`ConfirmButton`; "Cancelar" se confundiria com "Cancelar inscrição"). Pedem confirmação: publicar, iniciar sem check-in, excluir rascunho, sair da comunidade, remover membro, tirar do torneio, desmarcar check-in de alguém, marcar desistência, dar W.O., cancelar a própria inscrição, revogar link de convite ou de inscrição, sortear o seeding quando a ordem foi mudada. Desfazer o início e transferir a posse continuam pedindo para digitar o slug. O "sim" é vermelho quando a ação apaga ou tira algo; nas que só avançam (publicar, iniciar, W.O., sortear), tem a cor do botão principal.
- **Carregamento**: toda página que busca dado mostra, na hora, o lugar do conteúdo (título e linhas cinza pulsando) com o texto "Carregando…"; todo botão que chama a API fica desabilitado e com um indicador girando até a resposta.
- **Links e texto**: item de lista que abre página é a linha inteira, com o nome sublinhado na cor de link; links soltos e botões-link sempre sublinhados. Texto secundário numa cor própria com contraste AA (no lugar de opacidade). As regras e os motivos estão em "Princípios de interface" no `web/CLAUDE.md`.
- **Página que pede login** oferece "Entrar" e "Criar conta", os dois voltando para a página: quem chega por convite ou link compartilhado geralmente ainda não tem conta.
- **Publicar com o check-in já aberto** (rodada 2c, teste de ponta a ponta): se pela data e pela janela o check-in já devia ter aberto, publicar leva o torneio direto ao check-in, sem inscrições (a abertura automática vale ao ler). A regra da API ficou; o rascunho avisa antes no quadro da organização, o botão vira "Publicar e abrir o check-in" e a confirmação diz que não haverá inscrições, com a saída (mudar a data antes ou "Reabrir inscrições" depois). Assumido: avisar é reversível; fazer o publicar suspender a abertura automática (como reabrir) muda a API e fica para o usuário decidir.
- **Foco depois de agir** (rodada 2c): botão pendente não recebe `disabled` (o navegador tiraria o foco dele e quem usa teclado voltaria ao começo da página); fica com `aria-disabled`, ignora o clique e o Enter do formulário. Depois de uma ação cujo botão some no refresh, o foco vai para o bloco afetado: a linha do mapa na partida (confirmar, contestar, aceitar, resolver), o bloco da inscrição (inscrever-se, cancelar) e o quadro da organização (publicar, abrir o check-in, reabrir, iniciar, desfazer). O `ConfirmButton` devolve o foco ao botão quando a pergunta fecha (sim, não ou Esc).
- **Tela da partida desatualizada** (rodada 2c): sem tempo real, quem confirma um mapa que a organização já confirmou recebe o erro; a tela então recarrega os dados e mostra o estado de agora (o mapa confirmado e por quem).
- **Login e cadastro com sessão** (rodada 2c): quem já entrou e volta para essas páginas (pelo histórico, ou pelo link de novo) vê "Você já entrou como X" com "Continuar com esta conta", que leva ao `return_to`; o formulário continua embaixo, para entrar com outra conta.
- **Data de início que passou** (rodada 2c): enquanto a organização não inicia, a página diz "Início marcado para", não "Começa", que daria a entender que ainda vai começar.
- **Sessão que expirou no meio de uma ação**: o erro diz para recarregar a página e entrar de novo (recarregada, ela mostra "Entrar" e "Criar conta" voltando para lá).

- **Formulário de torneio** (pedido do usuário em 28/10, assumido o resto):
  - **Criar numa página só**, sem passos: à vista o que se decide sempre (nome, endereço, início, chave e séries); **fechados em acordeão**, com o resumo dos valores no título, os grupos que já vêm com padrão bom (Campeões; Inscrições e prazos: vagas, visibilidade, check-in, contestação); depois as regras adicionais e, por último, outros idiomas (a descrição fica junto do nome). Motivo: quase tudo tem padrão, e um assistente em passos faria clicar "Próximo" em telas sem nada a decidir; o resumo no título já serve de conferência. A data de início ficou à vista porque não tem padrão (é opcional).
  - **"Criar" mostra a revisão antes**: o Modal de confirmação traz o resumo (nome, início, formato, inscrições, campeões, idiomas) e avisa quando, pela data, o check-in já abriu. "Criar como rascunho" não pede confirmação. Três botões: Cancelar (ghost), Criar como rascunho (secundário), Criar (primário); Enter num campo vai para "Criar", que confirma antes.
  - **Editar em abas** (Geral, Formato, Inscrições e prazos), com um "Salvar" para todas; o campo recusado (pela API ou pela validação do navegador) abre a aba, o acordeão e o idioma dele antes de receber o foco (o formulário usa `noValidate` e confere antes de enviar, porque o navegador não abre nada sozinho e não mostra a mensagem num campo escondido).
  - **Descrição, regras adicionais e outros idiomas separados** (29/10, pedido do usuário; antes, descrição e regras num bloco com uma aba por idioma): a descrição fica junto do nome, as regras adicionais numa seção própria e, no fim, "Outros idiomas", um bloco por idioma diferente do original (o original é o da interface na criação), que começa sem tradução e se abre com "Adicionar Espanhol" (nome, descrição e regras adicionais desse idioma). Motivo: as abas escondiam a tradução e misturavam o original com ela. Remover uma tradução salva é tirá-la e salvar (o aviso diz que ela será apagada); adicionar de novo antes de salvar devolve o texto.
  - **A dica embaixo do campo diz só o que a opção escolhida faz** (29/10, pedido do usuário): repetição de campeões, visibilidade, check-in. O reset vira "Reset de grande final", com a explicação embaixo. Os textareas não têm mais "texto simples, as quebras de linha ficam".
- **Aba Regras: "Como funciona" + regras adicionais** (29/10, decidido com o usuário entre automático + adicionais, gerado e editável, e só o automático): a aba aparece sempre e começa com um texto curto gerado da configuração, em pt e es (nos `messages`, nada gravado, então muda com o torneio): inscrição, início e check-in com o horário de quem vê, chave, séries, campeões, envio e resposta do resultado, quem decide a contestação e o W.O. Só diz o que o sistema faz (o próximo mapa não espera a confirmação; sem resposta, o resultado vale; W.O. de quem não aparece é dado pela organização); print do placar entra quando existir. O campo `rules` vira, só na interface, **"Regras adicionais"** (mapas, conduta, queda de conexão), embaixo do automático e editável ali mesmo ("Editar regras adicionais", com Salvar e Cancelar; muda o texto que a pessoa está lendo: o da tradução no idioma dela, se tem, senão o original). Para quem joga, a seção só aparece com texto; para a organização, até o torneio encerrar. Bans e repetição de campeão aparecem como regras do torneio, mas o site ainda não as aplica (fica com o veto).
- **Resumo do formato com (i)** (29/10, pedido do usuário): valores curtos ("Único por série", "10 min" em "Prazo para contestar") e, ao lado dos termos que quem joga pode não conhecer (chave, campeões, check-in, prazo para contestar), um `InfoTip` (`Toggletip` do Carbon: abre ao tocar, porque o celular não tem hover) com as mesmas frases da aba Regras, e o link "Ver as regras".
- **Abas no celular sem as setas de rolagem** (29/10, o usuário viu as abas tremendo no celular): as setas do Carbon aparecem e somem conforme a rolagem e mudam a largura da barra, que reajusta a rolagem; abaixo do `md` elas saem (`TabList` de `shared/ui`) e a barra rola com o dedo. Junto, a tabela nunca alarga a página (`contain: inline-size` no `DataTable`, que rola por dentro): a da aba Organização passava da tela e arrastava a barra de abas.
- **"Inscrever alguém" sempre à vista** para a organização na aba Inscritos (até o torneio começar): sem vaga ou com todos os membros já inscritos, o Modal diz por que não dá e o que fazer (aumentar as vagas, gerar link de inscrição). Antes o botão sumia nesses casos e parecia não existir.

## Interface (Carbon)

Decididas em 28/10/2026, ao adotar o Carbon Design System no MVP. O alvo página a página está em `docs/design.md`; o guia de código em `web/CLAUDE.md`.

- **Carbon v11 e só ele**: o Tailwind sai. Motivo: dois sistemas de espaçamento e cor convivendo derivam com o tempo, e o auditor do Carbon só ajuda se o código for Carbon. Como toda tela seria refeita de qualquer jeito, o custo de tirar agora é o mesmo de manter.
- **Uso esperado: computador, com a aba aberta de lado** (28/10, do usuário): a maioria deve abrir no computador e deixar a aba aberta durante o torneio. O celular continua atendido (390px, toque), mas não é o caso principal; isso corrige o "a maioria abre pelo celular" que motivava a falta de `SideNav`.
- **Tema segue o sistema**: `white` no claro, `g100` no escuro, como antes. Decidido pelo usuário (opções: só escuro, só claro).
- **Quem usa escolhe o tema** (28/10, pedido do usuário): claro, escuro ou o do navegador (o padrão), no painel da pessoa no cabeçalho (o mesmo de Conta e Sair; sem sessão, o de Entrar), com o `ContentSwitcher` de ícones do seletor de tema do tutorial do Carbon. Fica no `localStorage`, não na conta: vale sem login e não custa rota nem coluna; um script no `<head>` aplica antes da pintura.
- **Uma coisa por tela, o resto em abas por sub-rota**: comunidade (torneios, membros, convites, configurações) e torneio (visão geral, chave, inscritos, regras, organização). Motivo: as páginas listavam tudo numa coluna só (inscritos sem paginação em cima das regras); sub-rota dá link direto, `loading.tsx` por aba e menos dado por página. `members`, `invites` e `settings` viram slugs reservados de torneio.
- **Listas grandes em `DataTable` com busca e paginação no cliente** (25 por página). A API não pagina: as listas são limitadas pelo tamanho do torneio ou da comunidade, e paginar no servidor fica para quando uma lista for ilimitada.
- **Confirmação em `Modal`** (kind `danger` quando apaga ou tira algo), no lugar da pergunta inline: o texto continua dizendo o que vai acontecer, o primário tem o nome da ação, "Não" é o secundário e o foco volta ao gatilho. A regra "nada de `confirm()`" continua.
- **Messages por namespace** (`messages/<locale>/<Namespace>.json`): um arquivo por domínio, como o resto do código, para fluxos em paralelo não escreverem no mesmo arquivo.
- **Fonte IBM Plex pelo `next/font`**, sem CDN, para não depender de rede externa em runtime.
- **Trabalho em agentes**: uma base (biblioteca, casca, guia, home) antes dos fluxos; depois fluxos A–D em paralelo, donos de arquivos disjuntos. O usuário quis comparar Opus e Sonnet nos fluxos com os mesmos briefs, em branches a partir do mesmo commit da base. Resultado: estrutura igual nas duas; Opus com melhor julgamento de detalhe (um título por página, erro de campo com foco, uma ação primária por papel) a 1,65× os tokens e o dobro do tempo. A variante Opus foi mesclada. Daqui em diante: Opus para o que pede julgamento de interface; Sonnet para trabalho com guia claro (migração mecânica, correção pontual, tela que copia um padrão).
- **Página da pessoa fora das abas da comunidade**: mesma URL (`/[tenant]/members/[user]`), mas com cabeçalho próprio, para a página ter um só título e o breadcrumb dizer de onde veio (Membros).
- **Formulários enviam por `onSubmit`, não por `action`**: o `action` do React reseta os campos controlados (os selects voltavam ao valor errado). `submitAction` continua.
- **Ações da organização na linha do mapa**, não no acordeão fechado: resolver uma contestação não pode ficar escondido. O acordeão fica com o W.O. e o histórico.
- **Suas comunidades no cabeçalho** (28/10, pedido do usuário): para ir de uma comunidade a outra sem voltar ao início, uma ação na barra (como a do idioma) com a lista e "Criar comunidade". A lista é buscada só ao abrir o painel (`GET /tenants` pelo navegador): no layout, ela custaria uma leitura da sessão no Redis a cada página e a cada recarga do tempo real. A última lista que chegou aparece na abertura seguinte, enquanto a nova é buscada.
- **Organizador que também joga**: a ação de jogador dele (inscrever-se, check-in) fica como terciária ou no `Tile` "Sua situação", para o cabeçalho ter uma primária só (a da organização).

## Notificações

- MVP: no site pelo WebSocket e no navegador por Web Push (também com a aba fechada).
- **Discord** (decidido pelo usuário em 28/10): por **webhook por comunidade**. O owner cola a URL do webhook de um canal e o site posta lá. Nada de bot nem DM.
- **Email**: nenhum aviso por enquanto. A cota grátis do Resend (100 por dia) fica para a conta (cadastro, recuperação de senha, troca de email).

### Avisos no Discord

O que não está acima é decisão minha (28/10), fácil de mudar:

- **Configuração** (`discord/`, `GET`/`PUT`/`DELETE /tenants/{slug}/discord` e `POST .../test`), só do owner, nas configurações da comunidade: URL, "Enviar teste", quais avisos, idioma das mensagens (pt ou es), "mencionar jogadores" (ligado por padrão) e remover. Uma configuração por comunidade (`discord_webhooks`, chave `tenant_id`).
- **A URL é credencial.** Só `https://discord.com/api/webhooks/{id}/{token}` e as variantes `discordapp.com`, `ptb.` e `canary.` (como a API faz requisições para o endereço, qualquer outro host seria uma porta para serviços internos; o cliente também não segue redirecionamentos). Vai para o banco separada em id e token, em claro, porque o envio precisa dela (a regra de guardar só o hash vale para segredo que a API só confere; aqui ela precisa usar). A API devolve só o id do webhook; a URL e o token nunca saem em resposta nem no log (os erros do `reqwest` perdem a URL antes de logar).
- **Avisos** (cada um ligável, `events` guarda os códigos): check-in aberto, torneio iniciado (link da chave), partida pronta, hora de iniciar e mapa contestado (para a organização), torneio encerrado (pódio) e resultado de cada série, **desligado por padrão** (é muita mensagem). O banco só confere a forma do código; quais existem é o `CATALOG` (`discord/catalog.rs`), então um aviso novo (o "veto começou") entra com **uma linha lá** (código do `Notice`, se vem ligado, a quem se dirige, texto em pt e es) e uma chave `events.<código>` no `Discord.json` do front, sem migration. Configurações antigas não ligam o aviso novo sozinhas.
- **De onde vêm**: os `Notice` que já existem para o Web Push e o evento novo do outbox `announce` (`outbox::Announce`: `tournament.started`, `tournament.finished`, `match.series_decided`, que só vão para o canal e não aparecem no OpenAPI nem no front). A comunidade sai do primeiro segmento do `path` do aviso. O despachante põe na fila do Discord na mesma transação em que lê o outbox (num savepoint: falha da fila não derruba o push nem o tempo real).
- **Menção**: quem vinculou o Discord à conta (`user_identities`) é mencionado (`<@id>`) em "partida pronta" (os dois lados viram uma mensagem só, "<@a> vs Bia") e nos avisos da organização, se "mencionar jogadores" está ligado. `allowed_mentions` lista só essas pessoas (`parse` vazio: nunca `@everyone`, `@here` nem cargos). Nos jogadores sem vínculo, o apelido; na organização, só quem vinculou. Apelidos e nomes de torneio vão com os caracteres do Markdown e o `@` escapados.
- **Fila própria** (`discord_messages`), esvaziada por uma tarefa da API (acordada pelo despachante, e a cada 15 s): o Discord limita o ritmo por webhook (~5 mensagens por 2 s) e o despachante não pode esperar por ele. Uma mensagem por vez, em ordem. Resposta 429 (`retry_after`) ou janela esgotada (`X-RateLimit-Remaining: 0`, `Reset-After`) põem **o webhook** em espera (`retry_at`), e as outras comunidades seguem. Pelo menos uma vez, como o push: a mensagem só sai da fila depois do 2xx, e a reserva de 2 minutos cobre quem cair no meio. 401 ou 404: o webhook foi apagado, a configuração fica `broken_at`, a fila dela é descartada, nada mais entra e a tela pede outra URL (colar uma nova desmarca). Outra falha (rede, 5xx): até 5 tentativas com espera de 30 s que dobra; 4xx: descarta com log. Mensagem com mais de 1 hora na fila é descartada (a partida pronta de ontem não serve).
- **Mensagens iguais se juntam** só onde o catálogo diz (`merge`: partida pronta, que chega uma vez por lado): a fila guarda os dois lados na mesma linha.
- **Texto**: exceção registrada à regra "a API devolve códigos". A mensagem sai da API para o Discord, sem passar pelo front, então o catálogo de textos pt/es fica no `discord/catalog.rs` (como o email em `auth/emails.rs`). Descartei ler `web/messages` com `include_str!`: o Render compila só `backend/` e o build não enxerga `../web`. Links com `WEB_ORIGIN` e o idioma da configuração; o nome do torneio, na tradução daquele idioma quando houver.
- **Sem variável de ambiente nova.** A base `https://discord.com` só muda nos testes (`Webhooks::with_base`, com um Discord de mentira).
- Não emite no outbox ao mudar a configuração: só o owner a vê, e a tela recarrega depois de salvar.

## Tempo real e avisos

Decidido em 28/10 (o usuário escolheu Web Push já neste incremento e os avisos da organização; o resto é padrão meu, fácil de mudar).

- **Canal**: um WebSocket por aba em `GET /ws`, autenticado pelo cookie de sessão no upgrade (o navegador já fala direto com a API; em produção o cookie é do domínio comum), com o `Origin` conferido contra `WEB_ORIGIN`: sem isso, outro site abriria o socket com o cookie de quem o visita. Sem sessão, 401 antes do upgrade. Ping a cada 30 s, porque proxy derruba conexão parada.
- **Assinaturas**: a aba pede o que a página mostra (comunidade; comunidade + torneio), e a API confere o acesso como na leitura (`TenantMember`, `can_see`). O canal da própria pessoa vem sozinho.
- **O que trafega é o aviso de mudança, não o dado**: tópico, tipo e, quando houver, a partida, nada que a pessoa não pudesse ler. A página pede de novo à API (`router.refresh()`), com o mesmo controle de acesso. Motivo: chave e partida dependem de quem vê (tarefas, destaques), e montar isso de novo no socket duplicaria a lógica. Pela cota do Redis (cada refresh lê a sessão), a aba junta os avisos de ~1,5 s num refresh só e ignora os que não são da página dela (a partida só recarrega pela própria partida; a chave, por qualquer uma).
- **Outbox**: quem muda o estado grava os eventos na tabela `outbox` na mesma transação; depois do commit, um despachante (uma tarefa da API, acordada pela rota e pelo agendador) lê, publica no `tokio::broadcast`, manda os Web Push e apaga. Motivo: só sai evento de transação confirmada, push não se perde se a API cair entre o commit e o envio, e há um lugar só para despachar (com `LISTEN/NOTIFY` se um dia houver mais de uma instância).
- **Agendador**: tarefa da API a cada 10 s, com advisory lock do Postgres (com mais de uma instância, só uma roda): confirma os mapas vencidos (`apply_due_confirmations`), abre o check-in que chegou na hora, avisa "hora de iniciar" uma vez por torneio (marcado no banco), recalcula o rating das comunidades marcadas (ver "Rating") e executa as exclusões de conta e de comunidade que venceram (ver "Excluir conta e excluir comunidade"). Aplicar ao ler e agir continua, para quem chega antes do agendador ver o estado certo; o evento sai de quem fez a transição, seja quem for.
- **Acesso perdido na hora**: quem sai ou é removido de uma comunidade (ou perde a comunidade, excluída na data agendada) recebe o aviso no próprio canal, perde as assinaturas daquela comunidade e a aba recarrega (cai no "sem acesso"). Sessão encerrada (sair, encerrar sessão, pedir a exclusão da conta) fecha os sockets dela.
- **Avisos** (notificação, além de recarregar): para quem joga, check-in abriu (inscritos), partida pronta (os dois lados) e adversário enviou um mapa (com o prazo para confirmar ou contestar); para organizer e owner, contestação a resolver e hora de iniciar (o início marcado chegou e o torneio não foi iniciado; iniciar continua manual). "Veto começou" entra com o veto.
- **Web Push**: service worker, chaves VAPID em variável de ambiente (opcionais: sem elas a API sobe e o push fica desligado, como o Discord), tabela de inscrições do navegador por usuário (endpoint único, com o idioma de quando se inscreveu), envio pela API com `web-push-native` (só cifra e assina; o HTTP é o `reqwest` que já existe), inscrição apagada quando o serviço responde 404 ou 410. No iPhone só funciona com o site instalado na tela inicial (por isso o manifest).
- **Texto do aviso**: a API manda código, parâmetros e o endereço, nunca texto; o service worker traduz com `messages/<idioma>/Notifications.json`, embutido nele por uma rota do Next que gera o script, no idioma da inscrição.
- **Aba visível**: o service worker não mostra notificação, porque a página já mostra um `Toast` com som pelo WebSocket. Sem push (negado ou sem suporte), o aviso com o site aberto continua pelo WebSocket. Som curto gerado pelo Web Audio (sem arquivo), ligado por padrão e desligável na conta (preferência do navegador).
- **Aba escondida** (28/10, pedido do usuário, porque o uso esperado é a aba aberta de lado): o aviso fica guardado e vira toast, sem som, quando a aba volta a ser vista; enquanto isso, o título da aba mostra quantos chegaram e o último ("(2) Sua partida está pronta"). Se este navegador não recebe Web Push, o som toca também com a aba escondida, porque nada mais avisaria; com push, quem avisa é a notificação do sistema (o Windows pode silenciá-la durante um jogo em tela cheia, e por isso o toast e o título ficam). A reconexão continua com a aba escondida, com espera de 1 s, 5 s, 30 s, 2 min e depois a cada 5 min (cada tentativa lê a sessão no Redis, e uma aba esquecida com a sessão vencida tentaria para sempre); ao voltar a ser vista, a tentativa marcada sai na hora. O que chegou com o socket caído continua perdido (sem replay): reconectar recarrega a página.
- **Permissão**: nunca pedida ao abrir o site; botão "Ativar avisos" na conta (aba própria, com o som e o estado deste navegador) e no tile "Sua situação" de quem está inscrito num torneio que não acabou.

Como ficou o backend (28/10; o que não estava acima é decisão minha, fácil de mudar):

- **Domínios**: `outbox` (eventos e `emit`; só depende de `shared`, para todo domínio emitir, inclusive `auth`, que fecha os sockets de uma sessão encerrada), `push` (inscrições e envio) e `realtime` (socket, despachante e agendador, acima de todos). Cada domínio monta os eventos dele: `tenants::changed`/`access_lost`, `tournaments::changed`/`check_in_opened`, e a chave em `matches::changes`.
- **Tabela `outbox`**: o evento em jsonb (`kind`: `tenant`, `tournament`, `me`, `access_lost`, `sessions_ended`, `notice`), com a transação que gravou (`xact`) e índice único em `(xact, md5(event::text))`: o mesmo evento repetido numa transação entra uma vez (pelo md5 porque a lista de inscritos de um torneio grande passaria do tamanho de uma linha de índice). O despachante pega até 200 por vez em ordem, com `for update skip locked`, publica, manda os push e só então apaga: se a API cair no meio, o push sai de novo (pelo menos uma vez, nunca nenhuma). Evento que ele não entende sai com log.
- **Despertar**: uma camada de todas as rotas acorda o despachante depois da requisição que emitiu (sabe por uma variável da tarefa que o `emit` marca), de qualquer método: ler também emite (abrir o check-in, confirmar por tempo). O agendador acorda a cada passada, o que cobre o resto em até 10 s.
- **Quem recebe o quê**: mudança de torneio vai para a comunidade (a lista mostra status e inscritos), para o torneio e para "Seus torneios" de todos os inscritos (e de quem acabou de sair deles). Na chave, `settle` compara cada partida antes e depois (estado, mapas, série) e emite uma mudança por partida que mudou, com "Seus torneios" de quem joga nelas; se o torneio encerra ou reabre, a mudança do torneio inteiro. A assinatura de um torneio também recebe a da comunidade dele (apelido e papel aparecem na chave e nas ações). O link de inscrição revogado avisa só a comunidade (a página do torneio recebe por ela).
- **Home da organização** (`GET /me/organizing`): recarrega pelo `me` de organizers e owner ativos da comunidade (`tenants::organizing_changed`), só quando a lista dela muda: o `settle` emite quando o conjunto de mapas contestados da chave muda (contestar, resolver, corrigir ou anular o contestado, W.O., desistência), a mudança de um torneio que está na hora de iniciar emite junto (check-in, inscrição, reabrir, abrir o check-in), e emitem também o aviso de hora de iniciar do agendador, o iniciar de um torneio que estava na hora, o desfazer (apaga os contestados) e a edição que adia um torneio que estava na hora. Enviar ou confirmar um mapa sem contestação, corrigir um mapa confirmado e o check-in antes da hora não mandam nada à organização. Quem passa a organizar recarrega pelo próprio `me` (troca de papel e transferência da posse, para o novo owner).
- **Avisos**: `check_in.opened` `{tournament}`, `match.ready` `{tournament, match, opponent}`, `match.game_reported` `{tournament, match, game, opponent, confirm_by}`, `match.game_contested` `{tournament, match, game, player}` e `tournament.start_due` `{tournament}`; `tournament` é o nome no idioma original (no Web Push, o da tradução no idioma da inscrição, quando há; o toast do site aberto usa o original), `opponent` e `player` são apelidos. `match.ready` sai para a partida que passa a ter os dois lados sem estar decidida (também a série reaberta por correção, e todas as prontas ao iniciar); a que vira W.O. na hora já chega decidida. A contestação não avisa quem contestou, mesmo sendo organizer.
- **Hora de iniciar**: `tournaments.start_reminded_at`. Avisa quando `starts_at` chegou num torneio na inscrição ou no check-in sem aviso, ou com o aviso de antes de o início ser adiado para depois dele (adiar arma de novo). A migration marcou como avisados os publicados e não iniciados cujo início já tinha passado, para o primeiro deploy não avisar de uma vez torneios esquecidos.
- **Agendador**: advisory lock de transação (`pg_try_advisory_xact_lock`), que solta sozinho até se a tarefa morrer. Cada torneio na própria transação; o erro de um fica no log e não para os outros.
- **WebSocket**: o `Origin` é conferido antes da sessão (tentativa de outro site não gasta comando do Redis): 403 `realtime.origin_forbidden`, sem sessão 401, e 426 `realtime.upgrade_required` para quem não pede WebSocket. Até 32 assinaturas por conexão (`realtime.too_many_subscriptions`). Sessão encerrada fecha com o código 4001 (o front não reconecta); nas outras quedas, o front reconecta (também com a aba escondida, mais espaçado: ver "Aba escondida"), assina de novo e recarrega. O acesso é conferido ao assinar; depois, só o `access_lost` tira assinaturas (quem perde a inscrição num torneio privado continua recebendo os avisos de mudança dele até recarregar, só com slugs e códigos de partida que já tinha visto). A sessão vai nos eventos pelo id público (16 caracteres do hash, o de `/auth/sessions`).
- **Web Push**: o endpoint precisa ser `https` num nome de domínio (nada de IP, `localhost` ou porta), porque a API faz requisições para ele; uma lista fechada de serviços de push foi descartada por arriscar recusar navegador legítimo. Inscrever o mesmo endpoint com outra conta passa a inscrição para ela; tirar é sempre 204 e só apaga a do próprio. `TTL` de 1 hora (também a validade da assinatura VAPID), `Urgency: high`; 404 e 410 apagam a inscrição, outra falha fica no log e a inscrição fica; `last_used_at` marca a última entrega. `VAPID_SUBJECT` é opcional (sem ele, a origem do front), e um par de chaves que não confere impede a API de subir. Chaves geradas por `bun scripts/vapid-keys.ts`.

## Repositório

- Privado agora, público depois: nenhum segredo no código (`.env.example` versionado), histórico limpo desde o primeiro commit.
- GitHub Actions com cache de build Rust (o plano privado tem 2.000 min/mês).
- CI (`.github/workflows/ci.yml`): em pull request roda só o lado cujos arquivos mudaram (`dorny/paths-filter`), em push na `main` os dois; execução antiga do mesmo ref é cancelada. A conferência do `.sqlx/` regrava as queries num diretório à parte e compara (`diff -r`) com o versionado, reaproveitando as dependências já compiladas (cerca de 1 min), em vez de rodar `sqlx-prepare.ts`, que compilaria tudo de novo num `target` próprio. Só `.sqlx/` sobrando ou diferente seria invisível ao clippy offline, por isso a conferência existe.
- Banco de dev: cluster Postgres local (sqlx confere queries na compilação; os testes de rota dividem 4 bancos `_sqlx_test_*`, criados uma vez e esvaziados antes de cada teste; ver "Testes"). Usuário `tournaments` sem senha (`trust` no `pg_hba.conf`), restrito ao próprio banco e aos bancos de teste.

## Organização do código

Regras completas em `backend/CLAUDE.md` e `web/CLAUDE.md`, que o Claude Code carrega sozinho ao abrir arquivos dessas pastas. Uma skill dependeria de ser acionada e um doc importado na raiz custaria contexto em toda sessão.

- **Por domínio dos dois lados**, com os mesmos nomes (auth, tenants, members, invites, depois tournaments, matches...), e `shared/` para o genérico. A rota diz o domínio. Uma pasta `components/` com tudo junto ficaria difícil de navegar com o crescimento.
- **API: SQL só em `<domínio>/db.rs`**; `handlers.rs` faz HTTP, `types.rs` tem os DTOs. Achar uma query é abrir um arquivo, e handler com transação (criar torneio, reportar resultado) não fica longo.
- **Testes de rota num binário só** (`tests/api/`), um arquivo por domínio: no Windows cada binário de teste demora para linkar.
- **Front sem shadcn por enquanto**: primitivos próprios em `src/shared/ui` (Button, Input, Field, Alert, Avatar, Page), com os nomes de variante do shadcn, para ele entrar no mesmo lugar depois sem mudar quem usa.
- Componente ou arquivo que cresce demais ou acumula funções é quebrado; os sinais estão nos dois `CLAUDE.md`.

## Testes

Desde 2026-10-29, pedido do usuário depois de uma suíte levar perto de uma hora com outras sessões rodando ("7 minutos rodando teste é uma eternidade"; um cluster Postgres separado para os testes foi recusado):

- **Bancos reaproveitados** (`crates/api/tests/api/db.rs`): no lugar do `sqlx::test`, que criava e apagava um banco por teste, cada banco principal tem 4 bancos de teste (`TEST_DATABASES`), `_sqlx_test_<banco>_t<n>`, migrados uma vez e mantidos entre execuções; são recriados só quando as migrations aplicadas não batem com as do código. Antes de cada teste, `truncate ... restart identity` em todas as tabelas, e as linhas que as migrations gravam (campeões, mapas) voltam de uma cópia feita depois de migrar. O custo era o `drop database`, que força um checkpoint no servidor inteiro: um banco vazio levou 107 s para sair com três suítes rodando. Um banco só para todos os testes foi descartado: os testes contam com o banco vazio e rodam em paralelo, e uma transação por teste desfeita no fim não serve porque os handlers fazem commit das próprias transações. A suíte inteira passou de perto de uma hora para uns 40 s.
- **Uma suíte por vez na máquina**: o binário de teste pega um lock de arquivo na pasta temporária (`tournaments-api-tests.lock`) e o segura até sair; a suíte de outra sessão ou worktree espera, com um aviso no stderr. Duas suítes juntas no mesmo Postgres se atrasam mais do que uma depois da outra.
- **Testes que não cobrem nada novo saem**: um teste só fica se exercita um caminho, regra, código de erro ou constraint que nenhum outro exercita. Saíram a criação de rascunho (já em `draft_is_only_for_organizers_until_published`), "desfazer o início tira a chave" (o 404 da chave depende só do status, já testado) e o teste da conversão das séries antigas para mapas (`matches/migration.rs`), que conferia migrations já aplicadas em produção, que não mudam mais, e era o único a precisar de um banco sem migrations. Juntar testes pequenos num só ficou de fora: com os bancos reaproveitados, um teste a mais custa milissegundos, e o teste separado diz melhor o que quebrou.
